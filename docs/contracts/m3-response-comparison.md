# Compare a capture with a replay result

A result's c key opens a read-only comparison with its source request. Captured data stays on the left and the new result on the right at 80 × 24 and larger. Both columns scroll together, with paired fields aligned even when text wraps. Esc or c returns to the result; a further Esc returns to the draft. Opening, scrolling, revealing, or closing the comparison never sends a request. Returning resets header masking. The comparison uses the result's destination and source ID, even if the draft has since changed.

Show both destinations, response status, actual/reported version labels, duration with distinct labels, retained representations, and response headers. Status zero in HAR means unavailable, not an HTTP status. Missing replay headers mean no response headers were received, not an empty response. Do not calculate speedups or attribute differences to a protocol or server change.

Match header names case-insensitively using ASCII rules, sort names for stable display, and preserve repeated values in their recorded order. Compare values exactly as stored; do not trim whitespace, merge duplicates, split comma-separated lists, or infer semantic equivalence. Missing names are labelled as absent from the respective stored header list. Header values remain masked until v reveals them. Equality labels describe stored values, not full responses or request equivalence.

Body comparison concerns available bytes, never missing data treated as empty. HAR text contributes its UTF-8 bytes; decoded base64 contributes decoded bytes. NotRecorded and Undecoded are unavailable. Base64 describes the HAR container representation, not HTTP decompression. If either side reports non-identity Content-Encoding, decline byte comparison because Netscope does not establish that both retained representations have undergone the same content decoding. An unknown replay response is also unavailable.

For a complete replay with equal available bytes, say stored bytes match and keep capture completeness unproven. Different lengths (reported separately when one complete body is empty, since nothing is shared) or the first unequal byte are facts about stored representations, not proof of server behaviour. For any incomplete replay outcome, report only the shared prefix and its length, including an explicit no-overlap result for zero available bytes. Never claim two full bodies match from a partial prefix. Byte offsets start at zero, and are not character positions.

Compare full available representations within existing import/replay budgets; bound the comparison preview separately to 1 KiB of text or 128 bytes of binary data. Label shortened previews. Escape all terminal controls. Non-UTF-8 header values reveal hexadecimal bytes with the same bounded binary preview and a shortening label where needed. Do not add a body diff algorithm, content decoding, JSON normalization, saved results, or automatic resending in this slice.

Tests cover absent versus empty bodies, partial outcomes, encoded data, decoded base64, exact bytes and lengths, repeated and differently cased headers, missing status, and different destinations. Fixed buffers cover comparison at both sizes; navigation checks cover masking, scrolling, resize, stale results, unchanged capture data, and no send events. A live loopback terminal check opens and closes comparison after a real GET. The teaching chapter starts with what a reader can establish from two observations before explaining the Rust mechanisms used to represent that conclusion.
