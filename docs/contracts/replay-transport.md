# Replay transport decision

The [request-body extension](m3-request-bodies.md) adds POST, reviewed UTF-8 bodies, and managed body headers. Its rules supersede the original GET-only scope below; the transport and response limits still apply.


Selected October 10, 2026, before adding network dependencies: Hyper's HTTP/1 connection API, Tokio, and tokio-rustls with WebPKI roots. Hyper parses the HTTP of replay responses; replay uses no Netscope parser. (Netscope later gained its own bounded HTTP/1.1 framing inspector, `wire_http.rs`, but it reads packet captures only and is never on the replay path.) One connection carries one request, a GET or, since the request-body extension, a POST. Live SSE observation uses the same sender for one GET. There is no connection pool, redirect follower, HTTP retry loop, proxy discovery, cookie store, content decompressor, or credential provider. The network test [`redirects_and_disconnects_never_open_a_second_connection`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/tests.rs#L479) proves the redirect and retry parts: a local server answers once with a 302 whose Location names another path on the same server, or closes without answering, and the test then checks that the listener has no second connection waiting. The 302 is returned as a Complete result, and the disconnect as a failure, with no further attempt. Address resolution may produce several addresses to try before sending.

The connection parser accepts at most 100 response headers and 32 KiB including the status line; its read buffer is capped at 32 KiB. The same header-size limit applies to chunked trailers. Trailers are consumed but not retained. The application retains at most 2 MiB of body data; transport/TLS buffers are separate bounded overhead. A frame can contain excess bytes, but the application only checks whether one additional byte exists and never copies excess bytes into the result. Outgoing explicit headers are limited to 100 entries and 32 KiB including field separators, before sending. The client adds Host and `Accept-Encoding: identity` to every request. A POST also gets client-managed `Content-Type` (from the reviewed body format) and `Content-Length`. A live SSE GET also gets `Accept: text/event-stream`; review refuses a user-selected Accept header for that mode rather than replacing it. No other application headers are added, and hyper adds none of its own to a GET with an empty body.

Each operation uses a dedicated thread with a current-thread Tokio runtime. The terminal owns a cancellation sender and a one-result channel with capacity one. Ordinary replay has no progress channel. Live SSE adds a Tokio `watch` channel that holds only the newest cumulative snapshot ([live SSE contract](m6-live-sse.md)). A single absolute deadline begins when Send is accepted. The worker owns partial response data outside the cancellable exchange future, so stopping the exchange preserves bytes already copied. The connection future is polled within that exchange and is dropped with it, closing the socket before a result is delivered. A completion already delivered wins over a later cancel; simultaneous readiness inside the worker prioritizes cancellation, then deadline, then exchange completion.

The OS resolver used by Tokio may continue a blocking lookup after cancellation. Runtime shutdown waits zero additional time for blocking resolver work. Such work cannot access the draft or produce a late UI result. It may outlive the worker thread until the OS lookup finishes. All socket and TLS work belongs to the cancellable exchange. This limitation does not imply remote rollback: a server may already have acted.

TLS verifies the certificate chain and destination hostname against bundled WebPKI roots. No user option bypasses verification. Test-only configuration can trust a generated local CA. HTTP/2 and HTTP/3 are not enabled; HTTPS advertises only HTTP/1.1.

References: [Hyper connection builder](https://docs.rs/hyper/1.12.0/hyper/client/conn/http1/struct.Builder.html), [Tokio runtime shutdown](https://docs.rs/tokio/latest/tokio/runtime/struct.Runtime.html#method.shutdown_timeout), and [rustls client configuration](https://docs.rs/rustls/latest/rustls/struct.ClientConfig.html). The milestone contract remains the acceptance checklist; this decision alone is not evidence of passing checks.
