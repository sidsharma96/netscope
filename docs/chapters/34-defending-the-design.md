# Defending the design

Suppose an experienced network engineer reads Netscope's source and then questions you about it for an hour. They will not ask what a vector is. They will ask why a `-1` in a HAR is not a zero, why a TCP overlap is not resolved in favour of the first copy, why a 304 response with two length headers is labelled ambiguous, and what happens to a capture taken on a Mac's loopback interface. This chapter collects the answers in one place.

## How to use this chapter

The chapter is organised as the questions an expert would ask, in the order they would ask them. It begins with the foundations every later answer depends on: what a HAR timing means, how a capture file is laid out, how TCP numbers its bytes, how HTTP/1.1 marks where a message ends, how DNS compresses names, and how TLS sets up a verified connection. The decision tree follows. Each decision is headed by the question an interviewer would put, and gives the choice, the alternatives and why they lost, the invariant the choice protects, its cost, what happens when it fails, and links to the code. After the decisions come the threat and failure model, the known defects with proposed fixes, and the questions the chapter cannot yet answer.

Earlier chapters teach the same material slowly, for a reader who knows no Rust. This chapter assumes you have read them, or at least the packet chapters, and moves faster. Every code link points at a line on the main branch, and the documentation check confirms that the named symbol is still on that line.

## Foundations from first principles

### What a HAR timing records

A HAR file is a JSON document that a browser's developer tools write after a page load. Each entry describes one request and its response, and carries a `timings` object with seven stages: `blocked` (waiting in the browser's queue for a connection), `dns` (name lookup), `connect` (opening the TCP connection), `ssl` (the TLS handshake), `send`, `wait` (from the end of sending to the first response byte), and `receive`. The [HAR 1.2 specification](https://raw.githubusercontent.com/ahmadnassri/har-spec/master/versions/1.2.md) makes `send`, `wait`, and `receive` required non-negative numbers. The other four are optional, and each may be `-1`, which the specification defines as "the timing does not apply to the current request".

That wording matters. A browser that sends a second request on a connection it already opened performed no DNS lookup and no TCP or TLS setup for that request. The exporter writes `-1` for those stages. The value is not "we do not know how long it took". It says the stage did not happen. A separate convention applies to sizes: for `headersSize` and `bodySize`, HAR uses `-1` to mean "the info is not available". The same number has two meanings depending on the field.

Two more rules complete the picture. `ssl` is nested inside `connect` for compatibility with HAR 1.1, so adding the two double-counts the TLS time. And `time`, the entry's total, is defined as the sum of the stages that are not `-1`. Netscope stores each optional stage as one of four [`Timing`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/lib.rs#L11) values: `Missing` (field absent), `Unavailable` (the exporter wrote `-1`; the name predates this chapter and the interface shows it as "Not applicable (-1)"), `Milliseconds`, and `ExporterNegative` for a narrow nonstandard browser value. The importer adds up the known main stages, leaves `ssl` out, and warns when the [`sum`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/lib.rs#L507) differs from the reported total by more than 0.01 ms. It also warns when [`ssl`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/lib.rs#L520) is larger than `connect`, which the nesting rule makes impossible.

HAR timestamps (`startedDateTime`) come from the exporter's wall clock. Netscope parses them with an RFC 3339 parser in [`timestamp`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/lib.rs#L212), which accepts only the RFC 3339 profile of ISO 8601 (a full date, a time, and an explicit offset). HAR permits any ISO 8601 form, so a valid but unusual timestamp such as a week date is rejected.

### What a capture file contains

A packet capture records frames as a network interface delivered them. The classic PCAP format, described in the [IETF PCAP draft](https://www.ietf.org/archive/id/draft-ietf-opsawg-pcap-06.html), is a 24-byte file header followed by records. The header starts with a magic number whose byte order tells the reader whether the file is little- or big-endian and whether timestamps have microsecond or nanosecond fractions. It also holds the version (2.4), the snapshot length (the largest number of bytes kept from any frame), and the link type. Each record has a 16-byte header with seconds, the fraction, the captured length, and the original length, followed by the captured bytes. When the original length is larger than the captured length, the capture cut the frame.

The link type tells the reader what the first byte of every record is. Type 1 is Ethernet: a 14-byte header with two MAC addresses and an EtherType that names the next layer (0x0800 for IPv4, 0x86DD for IPv6, 0x8100 for a VLAN tag). Type 101 is raw IP, where the first nibble is the IP version. Types 228 and 229 are raw IPv4 and raw IPv6. Other interfaces produce other link types. macOS's loopback interface `lo0` writes type 0, `DLT_NULL`, which starts each frame with a 4-byte address-family value in the capturing machine's byte order. Linux's `-i any` pseudo-interface writes type 113 (Linux "cooked" SLL) or, with newer libpcap, 276 (SLL2), because frames from different interfaces have no common link header.

PCAPNG is a different container. It is built from typed blocks, can hold several interfaces with different link types in one file, and is what Wireshark and `dumpcap` write by default. Its first four bytes are `0A 0D 0D 0A`.

### How TCP numbers its bytes

TCP gives each direction of a connection its own byte stream and numbers the stream's bytes with a 32-bit sequence number. The connection's first segment in each direction carries the SYN flag and an initial sequence number (ISN) chosen by the sender. SYN occupies one sequence number, so the first data byte is ISN + 1. FIN, which ends a direction, also occupies one number. Every later segment says "my first payload byte is number S", and the receiver places the bytes at S, S + 1, and so on. Segments can arrive out of order, arrive twice, or overlap partly. The [TCP specification](https://www.rfc-editor.org/rfc/rfc9293#section-3.4) defines this sequence space.

Thirty-two bits run out. After 4,294,967,295 the next number is 0. A plain integer comparison then says 0 comes before 4,294,967,295, which is wrong for consecutive bytes. The fix is serial-number arithmetic, defined in [RFC 1982](https://www.rfc-editor.org/rfc/rfc1982): treat the numbers as points on a circle and say that `a` comes before `b` when the clockwise distance from `a` to `b` is less than half the circle, 2^31. In code, subtract with wrap-around and reinterpret the 32-bit result as a signed integer:

```text
distance = (b - a) mod 2^32, read as a signed 32-bit integer
a = 4294967290, b = 5     -> distance = +11   (b is 11 bytes after a)
a = 5, b = 4294967290     -> distance = -11   (b is 11 bytes before a)
```

The answer is correct only when the true distance is less than 2^31 in either direction. Two points exactly half a circle apart have no defined order. Real TCP adds PAWS ([RFC 7323](https://www.rfc-editor.org/rfc/rfc7323#section-5)), which uses timestamp options to reject an old segment whose sequence number has come round again. At 10 Gbit/s a flow wraps its 4 GiB sequence space in about 3.4 seconds, so fast flows need it.

Netscope computes each segment's offset from its group's first observed sequence number with exactly this trick, in [`wrapping_sub`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L140), and keeps only offsets within a 256 KiB span. That span is about 1/16,384 of the half circle, so the ordering is always defined. The 32 MiB file limit also makes it impossible for one file to contain a flow long enough to wrap, so Netscope does not need PAWS.

The 16-bit window field in each TCP header advertises how many more bytes the receiver will accept. [RFC 7323 window scaling](https://www.rfc-editor.org/rfc/rfc7323#section-2) multiplies that field by 2 to the power of a shift count from 0 to 14. Each side announces its shift count once, in its SYN segment, and scaling applies only when both SYNs carry the option. A capture that starts mid-connection cannot know the shift. Netscope does not parse TCP options, so it reports the raw field.

### How HTTP/1.1 marks where a message ends

TCP delivers bytes, not messages, so HTTP/1.1 must say where each message ends. A message is a start line, header lines, an empty line, and an optional body, with each line ending in CRLF (bytes 13 and 10). [RFC 9112 section 6.3](https://www.rfc-editor.org/rfc/rfc9112#section-6.3) gives the body-length rules in order, and the order is part of the rule.

First, a response to a HEAD request, and any response with a 1xx, 204, or 304 status, ends at the empty line, whatever its headers say. A HEAD response may carry `Content-Length: 500` to describe the representation it would have sent; it still has no body. Second, a 2xx response to CONNECT switches to a tunnel. Third, if a message has both `Transfer-Encoding` and `Content-Length`, Transfer-Encoding wins, and the message "ought to be handled as an error" because it may be a request-smuggling attempt. Fourth, if `chunked` is the final transfer coding, the body is chunked: each chunk is a hexadecimal size line, that many bytes, and CRLF, and a zero-size chunk is followed by optional trailer fields and an empty line. Fifth, a valid `Content-Length` gives the body length in bytes. Finally, a request with neither header has no body, and a response with neither header runs until the server closes the connection.

Request smuggling is the reason the third rule exists. If a front-end proxy uses Content-Length and the back-end server uses Transfer-Encoding, the two disagree about where a request ends. The leftover bytes become the start of a second request that the proxy never inspected.

### Persistent connections and Connection: close

Opening a TCP connection costs a round trip, and opening a TLS connection on top costs at least one more. HTTP/1.1 therefore keeps a connection open after a response by default, so the next request can reuse it ([RFC 9112 section 9.3](https://www.rfc-editor.org/rfc/rfc9112#section-9.3)). This is called a persistent or keep-alive connection. Either side can end it by sending `Connection: close`, which means "this is the last message on this connection". HTTP/1.0 worked the other way round: connections closed after each response unless both sides sent `Connection: keep-alive`.

Reuse depends on framing. The client can send the next request only when it knows the previous response has ended, so a response without Content-Length or chunked framing must be delimited by closing the connection, and that connection cannot be reused. HTTP/1.1 also allows pipelining, sending a second request before the first response arrives, but responses must come back in request order. HTTP/2 replaces pipelining with multiplexed streams, which the [connection-sharing chapter](28-sharing-a-connection.md) explains.

Netscope meets persistent connections in three places. In a HAR, a request on a reused connection shows `-1` for DNS and connect, and the optional `connection` field may hold an exporter's connection identifier; Netscope retains both without inferring a connection history. In a packet capture, one direction of a persistent connection carries several messages back to back, and the framing inspector reads up to eight of them. It does not act on `Connection: close`, and it does not accept HTTP/1.0 start lines at all. In replay, each send opens one connection, sends one request, and drops the connection after the response. `Connection` and `Keep-Alive` are in the reserved list that [`validate_replay_header`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/replay.rs#L388) enforces, so a user cannot ask for different behaviour.

### Content negotiation and Accept-Encoding

One URL can have several representations: JSON or HTML, English or French, compressed or not. In proactive negotiation ([RFC 9110 section 12](https://www.rfc-editor.org/rfc/rfc9110.html#name-content-negotiation)) the client lists what it accepts in `Accept`, `Accept-Language`, and `Accept-Encoding`, optionally weighted with `q` values, and the server picks one. The response names the choice in `Content-Type`, `Content-Language`, and `Content-Encoding`. It should also send `Vary`, listing the request headers that influenced the choice, so a cache does not serve a French page to an English request.

Content-Encoding and Transfer-Encoding are different layers. Content-Encoding (`gzip`, `br`) is a property of the representation: the bytes the server describes are compressed. Transfer-Encoding (`chunked`) is a property of one HTTP/1.1 hop and is removed by the receiver. `identity` in Accept-Encoding means "no encoding".

A current browser sends something like `Accept-Encoding: gzip, deflate, br, zstd`, receives compressed bytes, and decompresses them. Its HAR export usually stores the decompressed text beside the original `Content-Encoding` header, so the recorded body and the transferred body are different byte sequences. Netscope keeps the recorded request and response headers as evidence of what was asked and answered. It does not claim to know which server rule chose the representation.

Replay sends `Accept-Encoding: identity` on every request and lets no user override it. The decision [why does replay force identity encoding](34-defending-the-design.md#why-does-replay-force-identity-encoding) explains the reason.

### How DNS compresses names

A DNS name such as `api.example.test` travels as a sequence of labels, each a length byte and that many bytes, ending with a zero byte: `3 api 7 example 4 test 0`. A label is at most 63 bytes, so its length byte has its top two bits clear. A whole name is at most 255 bytes. Answers often repeat a name from the question, so [RFC 1035 section 4.1.4](https://www.rfc-editor.org/rfc/rfc1035#section-4.1.4) allows compression: a two-byte pointer whose top two bits are both set and whose other 14 bits give an offset from the start of the message. The reader jumps to that offset and continues reading labels there. A name can be some labels followed by a pointer, or a pointer alone. The bit patterns 01 and 10 are reserved for other label types.

A pointer is a number taken from the packet. Nothing in the format stops it from pointing at itself, at a later pointer that points back, or past the end of the message. A reader that follows pointers without a limit can loop forever.

### TLS: the handshake, SNI, ALPN, and certificate checks

TLS turns a TCP connection into an encrypted, authenticated channel. In TLS 1.3 ([RFC 8446](https://www.rfc-editor.org/rfc/rfc8446#section-2)) the handshake takes one round trip. The client sends a ClientHello with the TLS versions and cipher suites it supports, a key share (its half of an elliptic-curve Diffie-Hellman exchange), and extensions. Two extensions matter here. Server Name Indication (SNI, [RFC 6066](https://www.rfc-editor.org/rfc/rfc6066#section-3)) carries the hostname in plain text, so a server hosting many sites can choose the right certificate; SNI may not carry an IP address. Application-Layer Protocol Negotiation (ALPN, [RFC 7301](https://www.rfc-editor.org/rfc/rfc7301)) lists the application protocols the client can speak, such as `h2` and `http/1.1`.

The server replies with a ServerHello containing its own key share. Both sides now compute the same shared secret and derive encryption keys from it, and everything after this point is encrypted. The server sends its chosen ALPN protocol, its certificate chain, a CertificateVerify message (a signature over the handshake so far, made with the certificate's private key, which proves the server holds that key), and a Finished message (a MAC over the handshake, which proves nobody altered it). The client checks all three and sends its own Finished. TLS 1.2 reaches the same result in two round trips with a different message order.

Certificate verification is what makes the channel authenticated rather than merely encrypted. The client builds a chain from the server's leaf certificate through intermediates to a root certificate it already trusts. It checks every signature in the chain, every validity period, that each issuer is allowed to issue certificates, and that the leaf is allowed for server authentication. It then checks that the hostname it connected to appears in the leaf's Subject Alternative Name list ([RFC 9525](https://www.rfc-editor.org/rfc/rfc9525)). A certificate can also be revoked before it expires; a client learns that from a certificate revocation list (CRL) or an OCSP response, and only if it checks.

Netscope's replay uses rustls 0.23 with the ring crypto provider and TLS 1.2 and 1.3 enabled. [`configuration`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L90) builds one client configuration per send. Its root store comes from [`TLS_SERVER_ROOTS`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L91) in the `webpki-roots` crate (version 1.0.9 in `Cargo.lock`), which is Mozilla's root program compiled into the binary at build time. The operating system's trust store is not consulted. The [`alpn_protocols`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L95) list contains only `http/1.1`. The hostname from the reviewed URL becomes a [`ServerName`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L211), which rustls sends as SNI and checks against the certificate; for an IP-address URL rustls sends no SNI and checks the IP against the certificate's IP entries.

### Wall-clock time and monotonic time

A wall clock reports the date and time and can jump: NTP corrects it, a person changes it, a virtual machine resumes. A monotonic clock counts elapsed time from an arbitrary start and never goes backwards. Rust's `Instant` is monotonic. HAR timestamps and PCAP record timestamps are wall-clock readings from the machine that made the file. Netscope's replay deadline, live SSE deadline, and live event times all use `Instant`.

## The decision tree

### Why store requests in a vector addressed by RequestId?

A [`Session`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L197) owns a `Vec<Request>` in file order, and every other structure refers to a request by [`RequestId`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L6), a wrapper around its index. The chronological order is a separate `Vec<RequestId>`, built once by [`sort_by_key`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L211) on (start time, file position). Host order and host membership are more ID vectors.

The invariant is that a request's identity never changes after import. Sorting, filtering, or searching permutes ID lists, never the requests, so a selection survives every view change. That works because the session is immutable once built: nothing is inserted or deleted, so indexes cannot go stale.

A `HashMap<RequestId, Request>` would give the same lookup with hashing on every access and no locality when iterating. A slot map or generational index exists to detect an ID that outlived a deleted element; with no deletion there is nothing to detect. Storing references (`&Request`) in the view lists would tie every view to the session's lifetime and make the borrow checker part of every screen. Indices cost one bounds check per lookup.

The typed wrapper stops a host ID being used as a request ID. It does not tie an ID to a particular session or prove it is in range; `RequestId` has a public field, so any code can construct one. Lookup through [`request`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L264) therefore returns an `Option`. The [collections chapter](08-structs-vectors-and-ids.md) teaches the Rust side of this.

### Why keep -1, missing, zero, and nonstandard values apart?

The foundation above explains what each value means. The decision is to keep all four distinct from import to display, using [`from_optional_har`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/lib.rs#L52), and never to turn any of them into a number for arithmetic.

The alternative most tools take is to clamp `-1` to zero and drop missing fields. That makes the stage sum agree with the total more often, and it is wrong: a zero-length DNS bar on a reused connection says "the lookup took no time", when the truth is "no lookup happened". The invariant is that a drawn duration always comes from a recorded non-negative number. The cost is a four-way match wherever a timing is displayed, and a consistency warning that fires on exports whose totals do not add up. Netscope reports the warning and does not repair either number.

### Why compute summaries and matches once, at import?

[`Session::new`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L209) sorts the chronological order, groups hosts, and runs redirect and retry matching before the first frame is drawn. Every later redraw reads stored results. For 10,000 entries the [large-capture measurements](../LARGE_CAPTURES.md) record a median import of 122 to 135 ms on an Apple M1, including this work.

Recomputing per redraw would repeat the same work at every key press for data that never changes. Lazy computation would move the cost to the first time a user opens the evidence tab. Incremental updates would only matter for a live recording, which Netscope does not have. The cost of the eager choice is startup time and memory for candidate lists, which are capped at 20 IDs per source.

Host grouping uses a `BTreeMap<&str, HostId>`, so each request costs O(log H) string comparisons for H hosts. The redirect and retry indexes are `BTreeMap`s keyed by URL text. None of these maps is iterated; they are used only through `get` and `entry`, so their sorted order buys nothing, and a `HashMap` would do the same job in expected O(1). No measurement favours either. The [architecture record](../ARCHITECTURE.md#derived-summaries-and-matching-indexes) records this.

### Why is binary search valid in redirect and retry matching?

For each 301, 302, 303, 307, or 308 response with one usable `Location`, the redirect matcher looks for later requests to the resolved URL that start after the source finished and within 30 seconds of that point. It first groups request IDs by normalized URL in [`by_url`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/redirects.rs#L35). The IDs are pushed while walking the chronological order, so each bucket is sorted by (start instant, file position). That is the sortedness invariant.

The matcher then calls [`partition_point`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/redirects.rs#L91-L94) with the predicate "the candidate starts at or before the source, or it starts before the source's reported end". Binary search needs the predicate to be true for a prefix of the list and false for the rest. Both halves of the "or" have that shape over a list sorted by start time: once a candidate starts after the source, every later one does too, and once the elapsed time reaches the source's duration, every later candidate's elapsed time is at least as large, because [`elapsed_ms`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/comparison.rs#L18) computes the difference exactly in integer nanoseconds before converting it, so it never decreases as the start time grows. An "or" of two prefix-true predicates is prefix-true. Ties in start time do not matter because the predicate depends only on the start time.

From that point the matcher scans forward, stops past the 30-second window, checks the method rule in [`method_matches`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/redirects.rs#L23) (a 303 must be followed by GET or HEAD; a 301 or 302 POST may become GET; otherwise the method must match), and stops after 20 matches. The retry matcher in [`retries::analyze`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/retries.rs#L27) uses the same search over buckets keyed by (URL, method) and compares headers, cookies, and query lists exactly.

Building the buckets costs O(N log N) for N requests. Each source then costs O(log k) for a bucket of k plus the scan. The scan stops after 20 matches but not after 20 rejections, so a capture where many same-URL requests fall inside one window and all fail the method or header check costs O(N^2) comparisons. The measured worst case in the large-capture record, 10,000 overlapping redirects to one URL, fell from 408 ms to 135 ms when this search replaced a linear scan.

### Why refuse pcapng and other link types, and what must a user do?

[`import_pcap`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L69-L84) accepts the four classic PCAP magic numbers and rejects PCAPNG at byte 0 with an explicit message. [`layers`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L171-L199) decodes link types 1, 101, 228, and 229. A file with any other link type still opens: every record is kept and shown, labelled "Link type unsupported; packet bytes retained", and none of them gets an IP, TCP, or UDP layer, so the streams view is empty.

The reason is scope, not difficulty. Each link type is a small header parser, and PCAPNG is a block parser with per-interface link types. Every addition is more input-handling code that must be bounds-checked and tested against hostile files, and the project chose to finish TCP reassembly and HTTP framing on a narrow input first. `DLT_NULL` needs a host-byte-order address family, so a correct reader must handle both byte orders and the different values BSD and macOS use for IPv6. SLL and SLL2 each have their own header layout. None of these is implemented, and no document warned about it until now.

To get a capture Netscope can read, capture on a real interface and save classic PCAP. On Linux, `sudo tcpdump -i eth0 -w capture.pcap` writes Ethernet frames in classic format, and `tcpdump -i lo` also works because Linux loopback uses Ethernet framing; avoid `-i any`. On macOS, `sudo tcpdump -i en0 -w capture.pcap` works for traffic to another machine, but traffic to `localhost` only crosses `lo0`, which produces `DLT_NULL`. For a local test server, either run the server on another machine or virtual machine, or rewrite the link type afterwards; `tcprewrite --dlt=enet` from the tcpreplay suite documents this conversion, though Netscope's tests do not exercise it. From Wireshark, use File, Save As, and choose the "pcap" format, or convert an existing file with `editcap -F pcap in.pcapng out.pcap`; the conversion fails if the PCAPNG file mixes link types.

Keep the snapshot length at 256 KiB or less; `tcpdump`'s default of 262,144 bytes is exactly the limit [`PCAP_RECORD_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L15). Stop the capture cleanly. Killing `tcpdump` can leave a half-written final record, and a [`"Truncated packet record"`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L143) fails the whole file. Keep files under 32 MiB and 20,000 records; [`PCAP_PACKET_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L111) rejects the whole file at the 20,001st record rather than keeping the first 20,000. Finally, capture on the receiving side or disable segmentation offload when you can. A sender with TCP segmentation offload hands the network card one large segment that the card splits, so a capture on the sender shows segments larger than the path allows, and some drivers record an IPv4 total length of 0 for them. Netscope's IPv4 [`total`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L217) length check rejects that as invalid. On Linux, `ethtool -K eth0 tso off gso off gro off` turns offload off for the duration of a test.

Fragmented IP packets are also refused. An IPv4 packet with the more-fragments flag or a fragment offset is labelled and not decoded further, and an IPv6 packet whose next header is not TCP or UDP, including a fragment header (44) or any other extension header, is labelled with its next-header number. Reassembling fragments is a second reassembly problem with its own overlap attacks ([RFC 5722](https://www.rfc-editor.org/rfc/rfc5722) forbids overlapping IPv6 fragments for that reason), and Netscope does not attempt it.

### How does Netscope turn TCP segments into a byte stream?

[`reassemble`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L87) makes two passes over the decoded packets.

The first pass groups segments into directed epochs. A direction is the ordered pair (source address and port, destination address and port); the reverse direction is a different group. An epoch is one connection's worth of that direction. The [`is_none_or`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L97) test starts a new epoch when the direction has none yet, when a SYN arrives and the current epoch has no SYN, when a SYN carries a different ISN, or when a SYN arrives after a FIN or RST closed the epoch. A retransmitted SYN with the same ISN joins the existing epoch. An active-epoch map keyed by direction makes this O(log F) per segment for F directions. At most [`FLOW_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L6) (128) epochs are kept. When the limit is reached, the direction's entry is removed from the active map and its later segments are counted as unassigned, so they can never be merged into an older epoch with the same addresses.

The second pass handles each epoch. The anchor is the first segment's sequence number (plus one if it is a SYN). Each segment's offset is its serial-number distance from the anchor. Segments with no payload and no FIN or RST are skipped by the [`declared_payload`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L142) check, because an ACK says nothing about the bytes. The epoch's span grows to cover every accepted segment, so data that arrives before the first recorded segment extends the span backwards, unless the epoch began with a SYN, in which case nothing may precede it. Then the code allocates two arrays the length of the span: the byte values and a [`ByteState`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L13) for each position (Missing, Observed, or Conflict), and writes every segment's captured payload into place.

Application parsing reads only [`contiguous_prefix`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L51), the bytes from position 0 up to the first position that is not Observed. A hole or a conflict ends the prefix, so the HTTP parser never sees two observed pieces joined across a gap. A segment whose header declares more payload than the capture kept contributes the captured bytes, and the rest of its range stays Missing.

The whole computation costs O(N log F) for the first pass and O(N + total payload + total span) for the second. Memory is two bytes per position: one in `bytes` and one in `states`, since a three-variant enum with no data occupies one byte.

### What happens when two segments disagree about the same byte?

Two copies of the same sequence range can carry different bytes. A sender may retransmit with different data, an attacker may inject a segment, or a capture may record a corrupted frame. Real receivers resolve this differently. Ptacek and Newsham's 1998 paper "Insertion, Evasion, and Denial of Service: Eluding Network Intrusion Detection" showed that operating systems disagree about which copy wins, and that an intrusion detector which picks differently from the target can be fooled. Snort's stream preprocessor and Suricata therefore let an operator set a per-host policy, with names such as first, last, bsd, linux, and windows, to match the target's behaviour.

Netscope does not know the receiving operating system and has no way to learn it from a capture. It picks no winner. The overlap rule, in the [`ByteState::Conflict`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L197-L199) match arms, counts an agreeing duplicate in `repeated_bytes` and turns a disagreeing position into `Conflict`. Conflict is permanent: a third copy that agrees with either version does not clear it. HTTP inspection stops at the first conflict.

The invariant is that every byte shown as stream content was seen, and every copy of it agreed. The cost is that harmless disagreements also stop parsing. Two common ones are known defects. A TCP keep-alive probe is sent with sequence number SND.NXT - 1, the last byte already sent, and [RFC 1122 section 4.2.3.6](https://www.rfc-editor.org/rfc/rfc1122#section-4.2.3.6) allows it to carry one garbage byte; Linux sends none, but stacks that do send one create a false conflict at the end of the data and cut the HTTP prefix there. A RST segment may carry data, which RFC 1122 section 4.2.2.12 suggests is diagnostic text, not stream content; Netscope sets [`reset`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L171) for such a segment but still places its payload into the stream like any other payload. Both are listed under known gaps with proposed fixes.

### How are memory and time bounded in reassembly?

Sequence numbers come from the file, so a hostile capture could claim a segment four billion bytes from the anchor. A dense array sized from that claim would exhaust memory. Netscope checks each segment, in file order, against two budgets before accepting it: the epoch's span must stay within [`STREAM_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L8) (256 KiB of positions), and the sum of all accepted spans must stay within [`TOTAL_STREAM_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L156) (8 Mi positions). A segment that breaks either budget is skipped and counted. The epoch keeps the segments that fitted, so which bytes survive depends on record order: a far-away segment recorded first sets the span and pushes out the ones near the anchor that come later. A skipped segment also prevents an observed-end result.

The 8 Mi budget counts positions. At two bytes per position the reassembly arrays can reach 16 MiB. The peak for a maximum PCAP import is therefore roughly the 32 MiB file buffer, plus up to 32 MiB of per-record copies (each record's bytes are copied out of the file buffer), plus 16 MiB of reassembly arrays, plus layer description strings: about 80 MiB. That figure is derived from the constants, not measured.

A sparse structure, such as an interval tree or a map from offset to segment, would allocate memory only for observed bytes and could accept larger spans with holes. It would make overlap comparison and the prefix scan more complex. With the span capped at 256 KiB the dense arrays are small, and the cap is what makes them safe.

### Why refuse Transfer-Encoding together with Content-Length?

[`inspect_http`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L140) reads the contiguous prefix of one direction and returns up to eight framed messages and the reason it stopped. When a message carries both headers, the [`transfer`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L231) check labels it "Ambiguous Transfer-Encoding with Content-Length" and stops.

RFC 9112 tells a receiver to let Transfer-Encoding win and to treat the message as an error. A server must pick one rule to keep working. An inspector should not, because the message's danger is precisely that two parties may have framed it differently. If Netscope applied the RFC rule, it would show one clean boundary when the real proxy in front of the server might have used the other. Labelling the message ambiguous is the conservative choice for a tool meant to reveal what happened. The cost is that a capture of a correct server receiving a smuggling attempt shows no further messages in that direction.

The same function accepts only a single `chunked` coding and only a single plain decimal Content-Length. `gzip, chunked`, repeated lengths, and `Content-Length: 5, 5` are all labelled outside the subset.

The check order has a defect. RFC 9112 applies the status rule (1xx, 204, 304 have no body) before the Transfer-Encoding rule. Netscope runs the [`status`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L235) rule after the ambiguity check, so a 304 that carries both headers is labelled ambiguous when it is unambiguously header-only. The fix is to swap the two blocks and add a test.

### How can a response be framed without seeing its request?

It cannot, in general. The framing inspector analyses each direction separately and never pairs a response with the request that caused it. It accepts only [`GET` and `POST`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L209) request lines, so a HEAD request in the other direction is not recognised, and nothing would pass that fact to the response side anyway. A response to HEAD that declares `Content-Length: 500` therefore makes Netscope wait for 500 body bytes, and on a reused connection it consumes the start of the next response as that body. A 2xx response to CONNECT has the same problem.

A response with neither length header is close-delimited: it ends when the server closes the connection. Netscope accepts that boundary only when [`observed_end`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L60) holds: the epoch began with a SYN, has a consistent FIN at the end of the data, no RST, no skipped segment, no notes, and no hole or conflict anywhere. Otherwise the message is labelled "Close-delimited response; observed end unavailable". The end of a capture file is not the end of a connection.

Other limits are explicit. A start line or header line longer than 4 KiB, a header block over 32 KiB, more than 100 fields, more than 1024 chunks, and a chunk or Content-Length over 256 KiB each stop inspection with their own label. A 101 response stops inspection because the bytes that follow belong to another protocol.

### Can a malicious DNS packet hang the parser?

No, but not for the reason the code comment suggests. The name reader [`name`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/datagrams.rs#L7-L49) requires every compression pointer to [`target`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/datagrams.rs#L19) an offset earlier than the pointer itself. That rule alone does not prevent a loop. Consider a label `1 a` at offset 12 followed by a pointer at offset 14 that targets 12. The target is earlier than the pointer, so the rule allows it. The reader reads `a`, reaches offset 14 again, jumps back to 12, and repeats.

Two other limits end the loop. The reader takes at most 64 steps, where each label and each pointer is one step, and it rejects a name once its decoded labels exceed 255 bytes. In the example the 64-step cap fires first. Every slice is taken with a checked `get`, so a pointer or label length past the end of the message is an error, not a panic.

The cap has a cost. A legal name can have up to 127 one-byte labels within 255 bytes, so a long but valid name exceeds 64 steps and is rejected as a traversal-limit error. A tighter design would track visited pointer targets or limit only pointer jumps; for example, allowing at most 127 label steps plus a small number of pointer jumps would accept every legal name and still terminate.

### Why give each send its own thread and runtime?

When the user presses Send, [`Worker`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L312) starts an operating-system thread that builds a current-thread Tokio runtime, runs one exchange, and sends one [`ReplayResult`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L51) back over a channel of capacity one. The terminal loop polls that channel between key presses. A live SSE send also gets a Tokio `watch` channel, which holds only the newest cumulative snapshot; the UI reads it with [`progress`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L406), so a slow redraw skips intermediate snapshots instead of letting them queue.

The alternatives were a long-lived asynchronous runtime driving the whole terminal loop, or a shared response buffer behind a mutex. The first would restructure input handling, cleanup, and tests around async code for a program that sends one request at a time. The second needs locking rules and a consistency story for partial data. The per-send thread gives the response bytes one owner until they are handed over, at the cost of a thread and runtime setup per send. The [waiting chapter](17-waiting-for-a-response.md) and [sharing chapter](24-sharing-work.md) explain the mechanics.

### How do cancellation and the deadline decide the outcome?

[`wait_for`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L297) races three futures with a biased `select!`: the cancel signal, the absolute deadline ([`TIME_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L30), 10 seconds, measured from the moment the UI accepted Send), and the exchange. Biased means the branches are checked in that order, so if cancellation and completion are ready in the same poll, cancellation wins. The partial result lives outside the exchange future, so dropping the exchange closes the socket and keeps the bytes already copied. [`retain_body`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L271) copies at most [`BODY_LIMIT`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L28) (2 MiB) and reports `SizeLimited` when one more byte existed, without copying it.

On the UI side, a result is accepted only if its operation ID matches the running operation, so a late result from an abandoned send cannot overwrite a newer one. Dropping a `Worker` cancels and then joins the thread, so no network work outlives the editor. One thing can: Tokio resolves hostnames with the blocking `getaddrinfo` call on a helper thread, and [`shutdown_timeout`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L389) with zero time abandons that thread instead of waiting. The lookup cannot touch UI state, but it continues until the operating system returns.

Cancellation stops local waiting. It does not undo anything the server already did with a POST.

### Why does live SSE reparse its whole prefix on every read?

Live SSE observation sends one GET with `Accept: text/event-stream` and records, for each event, the time since Send when the read that completed it arrived. On every body frame [`observe`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/streaming.rs#L51-L74) appends the bytes, checks the whole retained buffer for valid UTF-8, runs the SSE parser over the whole valid prefix to count complete events, clones the snapshot to publish it, and the caller then copies the buffer again with [`clone_from`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/streaming.rs#L96).

An incremental parser would keep state for a partial UTF-8 character, a partial line, the current event's fields, and the last event ID, and would process each byte once. Reparsing reuses the same [`parse_sse`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/sse.rs#L76) as captured SSE, so live and captured events cannot disagree about where an event ends. The price is quadratic work. If a server sends the 64 KiB limit one byte per frame, the k-th frame touches k bytes in each of at least four linear passes (two UTF-8 checks, the parse, and two copies), and the sum over 65,536 frames is about 65,536 squared divided by two, roughly 2.1 billion bytes per pass. That is a calculated worst case, not a measurement. It is bounded by the 64 KiB and 100-event limits and the 30-second deadline, and a normal server sends events in far fewer frames.

The timestamps have limits the code cannot remove. They include DNS, TCP, and TLS setup, and they measure when hyper handed the application a frame, which comes after the kernel, TLS records, and hyper's own buffer. Several events that arrive in one read share one timestamp. They are not server send times.

### How does replay use TLS, and what is missing?

The TLS foundation above describes the configuration: rustls, Mozilla's root set compiled in, hostname verification, and ALPN restricted to `http/1.1`. ALPN is restricted because the hyper connection Netscope uses speaks only HTTP/1.1; if the server picked `h2`, the HTTP/1.1 client would send a request the server cannot parse. No option disables verification.

Several things are missing. There is no revocation checking: no CRLs are configured and a stapled OCSP response is not checked, so a revoked but unexpired certificate is accepted. The operating system's trust store is ignored, so a corporate network that intercepts TLS with its own root certificate makes every HTTPS replay fail. Every TLS failure from [`TlsConnector`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L213) is reported as the same message, "TLS handshake or certificate verification failed", with no reason or certificate details, and the result records only the total elapsed time, not separate DNS, connect, and TLS durations. Certificate Transparency is not checked.

Address selection is also basic. [`TcpStream::connect`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L207) resolves the host and tries each address in turn, returning the last error. It does not implement Happy Eyeballs ([RFC 8305](https://www.rfc-editor.org/rfc/rfc8305)), which races IPv6 and IPv4 attempts a short delay apart. If the first address is an IPv6 address that silently drops packets, the 10-second deadline expires before the operating system gives up on it, and the replay times out even though IPv4 would have worked.

### Why does replay force identity encoding?

The [`request`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/lib.rs#L99-L155) builder always sets `Accept-Encoding: identity`, and the header is reserved so a user cannot change it. The reasons are size and honesty. The 2 MiB limit should apply to the bytes Netscope retains. With compression, a small transfer can expand to far more than 2 MiB, so a decompressor needs its own output limit and its own failure states. Without a decompressor, the retained bytes are exactly what arrived.

A server may ignore the preference. If the response still carries a Content-Encoding other than identity, Netscope keeps the encoded bytes and the header, and does not claim they are decoded. Comparison then refuses to compare bodies: [`encoded`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/comparison.rs#L52) makes the result "content encoding prevents a common byte representation" whenever either the captured or the replayed response names an encoding. Most browser captures name one, so body comparison against a browser HAR is often unavailable for this reason. Replay's request also differs from the browser's, which asked for compressed content; that is a disclosed difference, not a reproduction.

## Threat and failure model

### Hostile input files

A HAR or PCAP file may come from anyone. The design assumes it can be malformed or hostile and aims for three properties: the program does not crash, does not use unbounded memory or time, and does not let file content control the terminal.

The workspace forbids `unsafe` code, and its Clippy configuration denies `unwrap` and `expect`, so a malformed file produces an error value rather than a panic. Byte access in the packet code uses checked `get` calls. The HAR importer reads at most 32 MiB plus one byte and stops, rejects more than 10,000 entries, rejects duplicate JSON object keys, and relies on serde_json's default nesting limit of 128 levels against deeply nested input; the [`Limits`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/lib.rs#L11) type holds the first two. PCAP has the file, record-count, and snapshot-length limits above. Reassembly, HTTP framing, DNS, SSE, and live SSE each have the limits described in their sections.

Captured text can contain terminal control sequences. A header value containing an escape sequence could move the cursor, change colours, or, on some terminals, set the window title. Captured text in the views passes through [`terminal_text`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/session.rs#L285) before display, which replaces each control character with a visible escape such as `\u{1b}`, and a view test feeds hostile control characters through the renderer. Error messages use fixed text and file offsets, not captured values, so a hostile file cannot inject content into an error either.

### Secrets inside capture and draft files

A HAR file contains every recorded request and response: cookies, `Authorization` headers, bearer tokens in query strings, form bodies with passwords, and response bodies with personal data. A PCAP of plaintext HTTP contains the same, plus DNS queries that list every host a machine looked up, IP and MAC addresses, and timing. Netscope reads both locally and never sends anything when opening a file. It does not redact what it displays. Share a capture only after removing what it should not carry; for HTTPS traffic, prefer exporting a HAR from the browser over capturing packets with an `SSLKEYLOGFILE`, because a key log file decrypts every session it covers.

Saved replay drafts are the one file Netscope writes. [`sensitive_saved_header`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/saved.rs#L27) removes nine header names from a saved draft: Authorization, Proxy-Authorization, Cookie, Cookie2, Set-Cookie, X-Api-Key, Api-Key, X-Auth-Token, and X-Access-Token. That is a denylist. An allowlist would have to guess which harmless headers a user needs, and would silently drop custom ones; a denylist keeps the request usable and misses credentials under other names, such as `X-CSRF-Token`, `X-Amz-Security-Token`, or `Private-Token`. The URL is saved verbatim, including any token in its query string, and so is the body. The file is created with mode 0600 through a temporary file that is written, synced, and renamed into place by [`replace`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-tui/src/saved_file.rs#L44).

### Crashes, clocks, and slow peers

If Netscope crashes while saving, the old file stays intact, because the new content goes to a temporary file first and only a complete, synced file is renamed over it. A leftover temporary file makes the next save fail with a message that names it, since the temporary file is created with `create_new`. The directory is not synced after the rename, so after a power loss the rename itself may be lost and the old file reappears.

A wall-clock jump on the machine running Netscope does not affect replay or live SSE, because both use `Instant`. A wall-clock jump on the machine that recorded a HAR does affect redirect and retry matching, which compare HAR start times: a backward step can make a follow-up appear to start before its source, and the matcher will not suggest it. PCAP timestamps are displayed but not used for ordering; reassembly uses sequence numbers and record order.

A slow or silent server meets the 10-second replay deadline or the 30-second live SSE deadline, both fixed when Send is accepted and never extended by progress. A server that drips one byte at a time can make live SSE do quadratic parsing work within that window, as described above. A slow terminal cannot slow the worker, because the `watch` channel replaces old snapshots instead of queueing them.

## Known gaps and pitfalls

Each of the following is true of the code on main today. The proposed fix is not implemented.

The HTTP framing inspector checks Transfer-Encoding with Content-Length before the status rule, so a 304, 204, or 1xx response that carries both headers is labelled ambiguous instead of header-only. Fix: move the [`status`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L235) block above the ambiguity check and add a test.

A chunk-size line with whitespace before the extension, such as `3 ;name`, is labelled malformed, though RFC 9112 section 7.1.1 allows it. A chunk-size line longer than 4 KiB reports "waiting for complete terminator" instead of a limit. Fix: trim trailing spaces and tabs from the [`size`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/wire_http.rs#L261-L270) field before validating it, and give the long-line case its own label.

A TCP keep-alive probe carrying one garbage byte at SND.NXT - 1 creates a false conflict, and RST payload is placed as stream data. Fix: in [`reassemble`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/reassembly.rs#L87), ignore payload on segments with RST set, and treat a one-byte segment that lies entirely inside already observed data, immediately before the highest observed position, as a probe rather than a conflict, with a note.

macOS loopback (`DLT_NULL`, 0) and Linux `-i any` (SLL 113 and SLL2 276) captures open with no decoded layers, and PCAPNG is rejected. Fix: add the three link-type headers to [`layers`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L171-L199) with tests in both byte orders.

An IPv4 total length of 0, written by some segmentation-offload captures, is rejected as invalid. Fix: when the total is 0 and the captured frame is longer than the header, use the captured length and label the packet as an offload capture, in the IPv4 [`total`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L217) length check.

A truncated final record fails the whole file, and the 20,001st record does too. Killing `tcpdump` commonly produces the first case. Fix: in [`import_pcap`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-import/src/pcap.rs#L69), keep the records already read and attach a file-level note instead of returning an error.

The DNS name reader rejects legal names that need more than 64 steps, and its backward-pointer rule does not on its own prevent loops. Fix: in [`name`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/datagrams.rs#L7), count label steps and pointer jumps separately, allowing 127 labels and a small fixed number of jumps, or require each pointer to target an offset earlier than the previous pointer's target.

Host summaries drop a status outside 0 and 100 to 599 without counting it. The HAR importer never produces one, but `Session::new` is public and does not validate. Fix: add an "other" count in [`record`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/hosts.rs#L46-L54), or validate in `Session::new`.

Body comparison says "Stored lengths differ; shared bytes match" even when one side is empty and nothing was shared. Fix: return a distinct label from [`DifferentLengths`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-net/src/comparison.rs#L32) when the shorter body is empty.

If Esc is pressed after the worker has already finished but before the UI has accepted the result, [`complete`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-tui/src/replay_view.rs#L161) shows "Operation stopped" while the retained result says Complete. Fix: base the message on the result's outcome rather than on the cancel flag, and add a test for this order.

Live SSE reparses and copies its whole buffer on every frame, which is quadratic in the number of frames. Fix: keep an incremental parser position, or reparse only when a frame contains a line ending.

The packet inspector prints every timestamp with nine fractional digits, so microsecond files show invented precision. Fix: in [`packet_lines`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-tui/src/packet_view.rs#L201-L208), print six digits when the file's resolution is microseconds.

Saved drafts keep the URL query and the body verbatim, and the credential denylist misses common token headers. Fix: extend [`sensitive_saved_header`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/saved.rs#L27) with `X-CSRF-Token`, `X-Amz-Security-Token`, and `Private-Token`, and show a warning in the save preview when the query contains a parameter named like a token. The saved-file rename is not followed by a directory sync; fix by syncing the parent directory after `rename` on Unix.

Replay TLS has no revocation checking, ignores the operating-system trust store, reports every TLS failure with one message, and connects to resolved addresses one at a time. Fix, in order of value: report the rustls error kind; add an option to load the platform trust store with `rustls-platform-verifier`; race address families as RFC 8305 describes.

The timing variant for `-1` is named `Unavailable`, which matches HAR's meaning for sizes but not for timings. The interface now says "Not applicable (-1)". Fix: rename the variant to `NotApplicable`.

The saved-draft source uses `RequestId(usize::MAX)` as a marker meaning "no captured request", inside the ID's own value space. Fix: store `Option<RequestId>` in [`SAVED_SOURCE`](https://github.com/sidsharma96/netscope/blob/main/crates/netscope-core/src/saved.rs#L151)'s place.

Some branches in reassembly and HTTP framing cannot be reached, for example the `continue` after a missing existing epoch and the `let ... else` on records that always have a TCP layer. They are harmless. Fix: remove them when the surrounding code next changes.

## Questions this chapter cannot answer yet

How much memory does a maximum-size PCAP import actually use? The 80 MiB figure is derived from constants; no measurement exists. Running the import under a heap profiler on a generated 32 MiB, 20,000-record file would answer it.

How long does the live SSE worst case take on real hardware? The 2.1 billion bytes per pass is a calculation. A local server that sends one byte per write would measure it.
