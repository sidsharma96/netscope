/book/start-here CHAPTER 01

Understanding a request with Rust

A browser asks for a list of books. The response arrives, but it takes longer than expected. You open the recording to see what happened. Which request was slow? Did the browser record its response body? What does the timing actually tell you?

Netscope helps you inspect that recording in a terminal. As we build it, we use those questions to understand Rust: how a program stores information, how it shares access to that information, and how it handles missing or invalid input.

This book assumes no Rust knowledge. You do not need to recognise Rust syntax before an explanation begins. New symbols and technical terms are introduced alongside the problem they help solve.

One request to follow

Our examples follow a browser requesting https://example.test/api/books. The response contains a short JSON list. Both the address and its captured traffic are invented, so you can experiment without needing access to a real service.

The recording is a HAR file, a JSON document exported by a browser or another capture tool. JSON represents data using named fields, lists, text, numbers, and a few other values. A HAR arranges those values into records of HTTP requests and responses. HTTP is the protocol the browser uses here to ask for a resource and receive a response.

A recording can be incomplete. A missing response body means the export did not retain it. We will keep returning to distinctions like this because a useful inspector must preserve what the recording actually says.

A path through the ideas

Start by reading a capture and deciding what you can conclude from it. Then meet Rust's values and functions through a method name and a status number. Ownership explains who keeps the request data alive; collections explain how to store many requests without losing their identity.

Once those ideas are familiar, missing values and errors become easier to describe. We then follow a file into the program and a selected request onto the screen. Grouping and redirect evidence show how to calculate useful summaries while preserving uncertainty. Later chapters explain how we check our work and define the first useful version.

The later sharing lesson asks when ownership, channels, locks, and atomics fit a problem. Shaping the program connects those choices to the package boundaries and alternatives. The decision record keeps the evidence and open questions beside the lessons.

You can also use the Rust index to return to a concept. Source links appear after the explanation they support. Reading the implementation is a useful next step, but it is not a prerequisite for understanding a chapter.

What you can try today

Netscope can open a local HAR, list its requests, and show a selected request's headers, body, and available timings. It also reports invalid input and inconsistent measurements. A host view groups requests by URL host and opens a filtered list without changing their IDs. The inspector also shows possible redirect follow-ups and repeated attempts, with missing evidence and ambiguity labelled. Protocol notes explain recognized version labels while keeping unrecognized or disagreeing labels visible. You can also prepare and review an editable GET or POST draft. Sending from a reviewed draft makes one new request and shows its result separately from the recording.

The first version walkthrough uses the supplied synthetic capture. The later replay chapters explain how to prepare a local request and wait for its result. The verification record keeps track of what has been checked.

Begin with an observation

In the supplied capture, find the request method, URL, response status, and body. A method such as GET names the requested operation; a status such as 200 describes the reported response outcome.

Then find one unavailable timing. Describe what you know about it without replacing the missing information with a guess. That is the first habit this book asks you to practise.

/book/running-a-program CHAPTER 02

How does source code become a command?

You have opened Netscope from its project directory several times. Now you want to type netscope from a different folder and inspect a capture there. What needs to exist for that command to work?

There are two separate steps. First, the Rust source must become an executable that your computer can run. Then the shell—the program reading your terminal commands—must find that executable. Understanding the difference helps explain why a successful build can still be followed by “command not found.”

Building creates another file

A Rust source file contains instructions written for people and the compiler. The compiler checks those instructions and translates them into a form the target computer can execute. Building also brings together code from the application's dependencies. The result includes an executable file: a program the operating system can start.

Cargo coordinates this work. It reads package information from Cargo.toml, selects dependencies under the lockfile rules, and invokes the compiler. In this project, the package that owns the terminal application is named netscope-tui, while its executable is named netscope. Package names and command names can differ.

Follow the arrows in this diagram as actions that produce or place files. Running the final file is a later action; compiling does not start the interactive application.

Illustrative diagram
Rust source + dependencies
          │
        build
          ↓
Executable in the build directory
          │
        install
          ↓
Executable in an installation directory
          │
          run
          ↓
A running process with its own memory

The source and executable are separate files. Changing a source file does not rewrite an already installed executable. You must rebuild and reinstall to make the installed command reflect your edits. Cargo's introduction to building and running explains that separation and its normal build locations.

The shell has to find the executable

Suppose an installation places a program in /example/tools/bin/netscope. Typing that full path tells the shell exactly which file to start. Typing only netscope leaves the location unspecified.

PATH supplies a list of directories where the shell searches for commands. On macOS and Linux, the entries are separated by colons. PATH is an environment variable: a named value made available to a process and normally inherited by processes it starts. It contains directories, not the Rust source code or a list of individual executable files.

Here is an illustrative search order, not a reading of your machine's settings:

Illustrative diagram
Command: netscope
PATH:    /example/tools/bin:/usr/local/bin:/usr/bin

         first directory   → look for netscope
         next directory    → try here if needed
         next directory    → continue the search

If the installation directory is absent from that search, the executable can exist while its short command name still fails. Running it by its full path separates a search problem from a program problem. If an older copy appears earlier in the search order, you may also run a different copy from the one you just built. The installation guide shows how to inspect that choice.

The working directory answers a different question: where relative file paths begin. If you run netscope capture.har from a folder containing that capture, the argument refers to the file there. It does not refer to a file beside the executable. Installing the program should not require keeping your recordings in the source checkout.

Build tools and runtime needs differ

Building Netscope requires Cargo, the Rust toolchain, and the dependencies needed for compilation. Once built, starting the installed executable does not invoke Cargo to compile it again. It still depends on the operating system and compatible runtime facilities; a binary built for one operating system and processor is not automatically usable on another.

The book and sample captures are useful companion files in the repository. They are not files the installed application secretly loads to interpret your own capture. A first-run test from another directory is useful precisely because it exposes accidental reliance on those nearby project files.

Cargo installation normally builds with its release profile and puts commands under the installation root's bin directory. A profile is a set of build settings; release settings generally enable optimization. Installation location can be configured. The Cargo install reference gives the exact options; the Netscope installation guide provides the commands for this checkout.

Ask the installed program what it is

Help and version output should work before you supply any capture. netscope --help explains accepted arguments and basic controls. netscope --version identifies the package version compiled into that executable. It does not inspect the current source directory or prove that two builds with the same package version contain identical code.

A command also returns an exit status, a small number that a shell or another program can inspect. Netscope uses zero for success, one for a file or runtime failure, and two for invalid arguments. This lets a script distinguish an unreadable capture from a misspelled option without interpreting every sentence of an error message.

After installing, open a new terminal or check your command search path, then ask for the version and help. Next, open a supplied capture from a different directory using its full path. Predict which part would fail if the executable were missing, if its directory were missing from PATH, or if the capture path were wrong. Those are three different failures, even though each begins with a command that does not do what you expected.

The entry-point contract records argument and exit-status rules. The command entry point chooses a mode, and the isolated installation check verifies that the resulting command works away from the checkout.

/book/reading-a-capture CHAPTER 03

What a capture can tell us

Our request for a list of books has a reported total duration of 45 milliseconds. Before drawing a timeline, we need to decide what that number describes and what the other timing fields mean. A diagram can look precise even when the recording is incomplete.

A millisecond is one thousandth of a second. In a HAR, the total duration and the durations of individual stages are values reported by the tool that made the recording. We retain those values, including disagreements between them.

Missing time is different from zero

Suppose the DNS timing is zero. DNS is the system used to look up an address for a hostname such as example.test. A recorded zero means the exporter reported zero at its measurement precision. It does not establish that no lookup work occurred.

Now suppose the DNS field is absent. The export gives us no timing in that field. HAR also permits the number -1 for an unavailable optional timing. Absence and -1 are different ways the file can represent missing information; neither reports a duration of zero.

This matters on screen. A bar with zero length suggests a known duration. A label such as Not recorded or Unavailable tells the reader that the duration is unknown. We need to preserve that distinction before choosing how to draw it.

Later, missing values and errors shows how Rust gives these states separate names. For now, the important question is what each observation allows us to say.

Some timings contain other timings

The sample reports 30 ms for connecting and 20 ms for TLS within that connection. TLS establishes the protected connection used by HTTPS. HAR includes its duration inside the connection duration.

Think of a 30 ms interval with a 20 ms portion inside it. Adding 30 and 20 would count that portion twice. The inspector therefore shows TLS as a detail of connecting. HAR calls this field ssl, so you will also see that name in the file and interface.

The waiting duration needs care too. It includes the time between sending the request and starting to receive its response. That interval can contain network delay and server work. A capture does not separate those causes merely by reporting one waiting value.

An observation and an explanation need different labels

A recorded status of 200 is a fact present in the file. A calculated total is a derived value: we obtained it by applying a stated rule to recorded numbers. Both are different from an inference, which proposes an explanation that the recording does not establish on its own.

For example, two similar requests might suggest a retry. They could also be independent actions. Calling the second request a retry needs more evidence or a visible explanation of the assumption.

A teaching diagram has another purpose. It may illustrate the messages exchanged while opening a connection, even though this HAR contains no record of those individual messages. We label that diagram as an illustration. Information the recording does not provide stays unavailable.

These labels make the reasoning readable. The reader can tell which claims came from the file, which came from a calculation, and which need further evidence.

An empty body is still information

A response body is the content returned with a response, such as our JSON list of books. A captured empty string means the export retained an empty text representation. An absent body field means it retained no body text.

Those cases may look identical if we immediately turn both into an empty string. Keeping them separate lets the inspector say either Captured body is empty or Response body not recorded. The distinction helps you investigate the recording without silently changing its meaning.

Try the distinction

A capture reports 30 ms for connecting and 20 ms for TLS. Explain why those values do not describe 50 ms of connection setup. Then describe what you would display if the TLS timing were -1.

Finally, imagine that a response body is absent. State one fact you can report and one conclusion the absence does not support.

Further reading

The HAR 1.2 specification describes the timing fields and their relationships. Netscope's input contract records the exact subset we accept. The contract is a reference for details; the distinctions above are the reason for those rules.

/book/values-and-functions CHAPTER 04

Values, names, and functions

Our capture contains the method GET and the status 200. To work with those observations, a program needs to store text and numbers, give them names, and perform small operations on them. This chapter introduces enough Rust to read those operations.

The examples are deliberately smaller than the application. Each one isolates an idea you can predict and check before combining it with other ideas.

Give a value a name

A variable gives us a name to use for a value. Rust introduces a variable with let. Here we name a number and a piece of text:

rust · teaching example
let status: u16 = 200;
let method: &str = "GET";
assert_eq!(status, 200);
assert_eq!(method, "GET");

Read the first line as "let status be a u16 with the initial value 200." The colon introduces the type, which describes the kind of value allowed here. The equals sign supplies the value. The semicolon ends the statement.

u16 stores an unsigned whole number using 16 bits. Unsigned means it cannot be negative. A bit can be zero or one; 16 bits can represent 65,536 different values, so this type holds numbers from 0 through 65,535. That is enough room for an HTTP status, although many numbers in that range are not valid HTTP statuses. Choosing a type and checking a captured value are separate tasks.

The second line stores a reference to text. Rust writes this type as &str: str describes UTF-8 text, and & means a reference to it. The quoted text is part of the program, so this example can refer to its existing bytes. The next chapter explains references alongside String, the type we use when a value needs to own its text storage.

The last two lines check our expectations. assert_eq! checks that its arguments are equal and stops the example with a failure if they differ. The exclamation mark identifies a macro, a construct that produces Rust code from its input. For now, use these assertions to state what an example should produce. We will return to macros when we need to understand more about how they work.

A type can come from context

You can also write let status = 200;. Rust can often work out a value's type from the operations around it. This is called type inference. When nothing else constrains a whole-number literal, Rust uses i32, a signed 32-bit integer type.

An explicit type can make an example clearer, but it does not convert the value. Writing let status: u16 = "200"; asks Rust to place text where a number is required. The compiler rejects it. Turning text into a number requires a parsing operation, which can fail if the text is unsuitable.

That distinction also appears when reading a capture. The JSON number 200 and the JSON string "200" have different types even though they look similar on a screen.

Make changes explicit

Selecting the next request changes a position in the list. Rust asks us to mark a variable as changeable with mut:

rust · teaching example
let mut selected = 0_usize;
selected += 1;
assert_eq!(selected, 1);

The suffix in 0_usize chooses the integer type usize. Rust uses this type for collection sizes and positions. Its size depends on the target platform. The += operation adds one and stores the result back in selected.

Without mut, Rust rejects that change. This gives the reader of the program a useful distinction: some values describe the capture, while others track choices the user can change.

Permission to change a number does not prove the new number identifies a request. A list may be empty. The collection chapter explains how we check a position before using it.

Put one decision in a function

HAR uses status zero to mean that no HTTP status was recorded. We can put the corresponding question into a function:

rust · teaching example
fn has_http_status(status: u16) -> bool {
    status != 0
}
assert!(has_http_status(200));
assert!(!has_http_status(0));

fn introduces a function. The parentheses describe its input: one value named status, of type u16. The arrow introduces the output type. bool has two possible values, true and false.

Inside the braces, != asks whether the status differs from zero. This last expression has no semicolon, so its value becomes the function's result. With a semicolon, that value would be discarded and the function would no longer provide the promised boolean result.

assert! checks a boolean condition. In the second assertion, the ! directly before the function call means "not." Its position matters: after a macro name, ! marks a macro call; before a boolean expression, it reverses true and false.

The function's question is deliberately narrow. A nonzero number is not automatically a valid HTTP status. We will validate the allowed range when accepting input.

Names have a scope

The parameter status belongs to the function body. A caller passes in a value and receives the result; it cannot reach inside the function merely by using that parameter's name.

This region in which a name is available is its scope. Braces often mark a scope in Rust. The ownership chapter adds the related question of when a value is cleaned up. Keeping names and values distinct will help: a name can stop being usable while its value has moved somewhere else.

Predict the answers for 0, 99, 100, 599, and 600, then check them with assertions. Explain why the new name fits this question better than has_http_status.

Put the statements you want to try inside fn main() { ... } in a scratch file named example.rs. main is the function a standalone Rust program begins with. Place any helper function beside it. The braces in this instruction stand for your actual statements, not the three dots.

/book/storing-requests CHAPTER 05

Who keeps a request alive?

You select a request in the list and open its details. Both screens need the same URL, headers, and response body. Copying all of that data for each screen would use more memory and create more values to keep consistent.

We can store the request once and let each screen read it. Rust asks us to make one part of that arrangement explicit: who is responsible for keeping the data alive, and who is only using it for a while?

A string owns its bytes

Text occupies memory. Rust's String type manages a region of memory containing UTF-8 text. UTF-8 represents characters as bytes, and a character can use more than one byte. A region reserved for this text is often called a buffer.

A String keeps track of the buffer's location, the number of bytes currently used, and the available capacity. It also takes responsibility for releasing the buffer when it is no longer needed. That responsibility is what ownership means in this example.

Consider giving a URL another name:

rust · teaching example
let url = String::from("https://example.test/api/books");
let request_url = url;

String::from creates an owned string from the quoted text. The second line transfers that string into request_url. Rust calls this a move. The text stays in the same allocated buffer, and request_url becomes responsible for it. The old name, url, can no longer be used to access the moved value.

This rule prevents two independent owners from both trying to release the same buffer. If we want a second owned copy of the text, we can request one with clone. That copies the string's contents and gives the copy its own storage.

Follow the move

Step through the diagram and watch the owner change while the text buffer remains in place. The drawing explains ownership; it does not promise a particular physical memory address or compiler layout.

A local variable belongs to a scope, the region of code in which its name is available. A function body is one example. When the owning value reaches the end of its lifetime, Rust normally runs its cleanup. For String, that releases the buffer.

Moving a value out of a function can give ownership to the caller. Leaving a function therefore does not always mean destroying everything it used. The useful question is where ownership went.

Borrow while drawing

A screen needs permission to read the URL, but it does not need to take over its storage. A shared reference gives it that access. Rust writes a reference with & in front of the type.

Here is a small teaching example. A struct groups named fields into one value; this one has only a URL field.

rust · teaching example
struct Request {
    url: String,
}

fn draw_request(request: &Request) {
    println!("{}", request.url);
}

The function receives &Request, a shared reference to a request. Calling this function lends it access to an existing value. The function can read the URL while the request's owner remains responsible for the data.

The dot in request.url selects the URL field. println! prints formatted text, and {} marks where that value appears. This small example writes one line; the application uses the same borrowing idea to draw a terminal screen.

A shared reference does not allow this function to replace the URL. Rust also checks that the reference cannot outlive the request it refers to. Together, those rules let a function read this data without taking ownership or using it after cleanup.

Some Rust types permit carefully controlled changes through shared references. We do not need those types for this request. The screen chapter introduces a mutable reference when selection actually needs to change.

Why store IDs?

Reading a request is a brief operation. Remembering which request you selected lasts across many screen updates. We can keep an ID in the navigation state and look up the request whenever we need to draw it.

That ID identifies an entry in the session, the collection of requests loaded from one capture. Keeping a number here avoids retaining a reference between screen updates. The next collection chapter explains how IDs and lookup work, including what happens when an ID has no matching request.

/book/structs-vectors-and-ids CHAPTER 06

Keeping requests together

A method and a URL describe the same request. If we store them as unrelated variables, every part of the program has to remember which values belong together. A capture with hundreds of requests makes that arrangement difficult to manage.

Rust gives us a way to group the fields of one request, and another way to keep many requests in order. We can then ask a separate question: how do we remember a request when its position on screen changes?

Group one request's fields

A struct defines a type with named fields. Here is a small request type with only the two fields we need for this example:

rust · teaching example
struct Request {
    method: String,
    url: String,
}
let request = Request {
    method: String::from("GET"),
    url: String::from("https://example.test/api/books"),
};
assert_eq!(request.method, "GET");

The first pair of braces defines the fields and their types. The second constructs a particular request by giving each field a value. Commas separate the fields. The dot in request.method selects the field named method.

Both fields own their strings. When the request is cleaned up, Rust also cleans up those fields. The grouping therefore records both the relationship between the values and who owns them.

Our full request has more fields, but the idea is the same. You can understand this small example before reading every piece of a HAR record.

Keep several values in a vector

A vector, written Vec<T>, is an ordered collection that can grow. The T stands for its element type: Vec<String> contains strings, and Vec<Request> contains requests. All elements in one vector have the same type.

To see how a vector grows, start with method names:

rust · teaching example
let mut methods = vec![String::from("GET")];
methods.push(String::from("POST"));
assert_eq!(methods.len(), 2);

The vec! macro creates a vector containing one string. Calling push adds another element at the end and transfers ownership of that string to the vector. Calling len returns the number of elements. We need mut because adding an element changes the vector.

A vector preserves order and permits repeated values. That makes it useful for captured headers too. Two headers with the same name can remain two separate entries in their original order.

A position may have no element

Positions begin at zero. In our two-element vector, GET is at position zero and POST is at position one. Position two does not exist.

The get method checks a position and returns an Option. A successful lookup contains a reference to the element; a failed lookup contains no element. The next chapter explains how to handle those alternatives.

This check matters when the user presses Down in an empty capture. There is no request to select, even though zero is a perfectly valid integer. A number's type alone cannot tell us whether it names an existing element.

Rust also permits direct indexing, such as methods[0]. An out-of-range direct index causes a panic, which stops ordinary execution. For a user-controlled selection, we use checked lookup and a defined empty state.

Sorting should preserve identity

Imagine three requests recorded in this order: request 0 starts at time 30, request 1 at time 10, and request 2 at time 10. These are invented times for the explanation.

We want the screen to show the earlier requests first, but we still want request 0 to mean the first entry in the capture. A second vector can store the display order:

Illustrative diagram
Request data stays here       The screen reads these IDs
0: starts at 30                1 → first row
1: starts at 10                2 → second row
2: starts at 10                0 → third row

The two requests with equal times stay in source order. Sorting the IDs changes the view without moving or copying the stored requests. An error referring to request 0 still points to the same source entry.

This costs some extra memory for the ID vector. It is useful here because we load a session once and read it many times. Editing or deleting requests would require another decision about how IDs survive those changes.

Give different IDs different types

A request ID and a host ID can both contain the number 2 while referring to different things. Wrapping the numbers in separate types lets the compiler catch accidental mixing:

rust · teaching example
struct RequestId(usize);
struct HostId(usize);
fn request_position(id: RequestId) -> usize {
    id.0
}
assert_eq!(request_position(RequestId(2)), 2);

These are tuple structs. Their fields use positions instead of names, so id.0 reads the first field. RequestId(2) constructs a request ID containing the number 2.

A function expecting RequestId does not accept HostId, even when the contained numbers match:

Rust · expected compiler error
struct RequestId(usize);
struct HostId(usize);
fn select_request(id: RequestId) {}
select_request(HostId(2));

This example is supposed to fail at compilation. Separate types protect the meaning of an ID. A lookup must still check that the request exists, and the application must use the ID with the session it came from.

/book/options-results-and-matching CHAPTER 07

Missing values and errors

The DNS timing in our capture might be absent, unavailable, zero, or a positive duration. It might also contain an invalid value. Before using the number, we need to answer two questions: was a value supplied, and can we accept it?

Rust gives these questions different types. Keeping them separate helps us avoid turning an invalid or missing measurement into a convincing number on screen.

Represent the possibility of absence

Option describes a value that may be absent. Option<f64> can be Some containing a number or None containing no value. The angle brackets identify the contained type. f64 is Rust's 64-bit floating-point type, which can represent fractional durations such as 30.125 milliseconds.

An option is an enum. An enum defines named alternatives, called variants, and a variant can carry data. Some(30.125) carries a number; None does not carry a hidden zero.

This is also the type used by a checked vector lookup. A successful lookup returns Some containing a reference to the element. An out-of-range lookup returns None. The same idea describes absence in different situations without pretending that a value exists.

A present number still needs a meaning

Some(-1.0) tells us that a number was supplied. It does not explain the special meaning HAR assigns to that number. For an optional timing, -1 means unavailable.

Our timing type therefore has three variants. Missing means the field was omitted. Unavailable means the exporter supplied -1. Milliseconds contains an accepted duration, including zero.

These names make later decisions clearer. Drawing a duration and displaying an unavailable label are different operations, and the stored value tells us which one applies. The value -2 fits neither case, so validation rejects it.

Give failure a value too

Result describes an operation that can succeed or fail. Ok carries the successful value; Err carries information about the failure. Both alternatives are ordinary values the caller can inspect.

The timing conversion returns Result<Timing, InvalidTiming>. The first type inside the brackets describes success, and the second describes failure. Here are checks against the implemented conversion:

rust · teaching example
use netscope_core::{InvalidTiming, Timing};
assert_eq!(Timing::from_optional_har(None), Ok(Timing::Missing));
assert_eq!(Timing::from_optional_har(Some(-1.0)), Ok(Timing::Unavailable));
assert_eq!(Timing::from_optional_har(Some(0.0)), Ok(Timing::Milliseconds(0.0)));
assert_eq!(Timing::from_optional_har(Some(-2.0)), Err(InvalidTiming));

The use line brings two names from the core library into this example. The braces group the names we want. In Timing::from_optional_har, the double colon selects a function associated with Timing. The same notation selects its named variants, such as Timing::Missing.

Read the first assertion in two steps. We supply no numeric value, represented by None. Conversion succeeds, represented by Ok, and the successful result records that the timing is missing. Missing data can therefore be a valid outcome. An invalid negative duration is a different outcome, represented by Err.

Handle the alternatives with match

Once a value has named alternatives, we need a way to choose what to do for each one. A match expression compares a value against patterns:

rust · teaching example
use netscope_core::Timing;
let timing = Timing::Missing;
let label = match timing {
    Timing::Missing => "Not recorded",
    Timing::Unavailable => "Unavailable",
    Timing::Milliseconds(_) => "Duration recorded",
};
assert_eq!(label, "Not recorded");

Each line inside the braces is a match arm. The part before => is its pattern; the part after it is the value to produce when that pattern matches. The underscore ignores the number inside Milliseconds because this example needs only a label.

Rust requires the match to cover every possible variant. That is useful when different stored states require different displays. If we later add another variant, a match listing each existing variant will need an explicit decision about the new case.

The timing conversion uses the same mechanism to inspect its input. It also checks that a supplied duration is finite and non-negative. Floating-point types have special values for infinity and "not a number," often called NaN, so accepting any f64 would be too broad.

Stop when the next step cannot proceed

Reading a request requires several successful checks. If a required field is invalid, there is no complete request to return. Writing out a full match for every check would repeat the same error-handling pattern.

The question-mark operator, ?, expresses that pattern:

rust · teaching example
use netscope_core::{InvalidTiming, Timing};
fn optional_dns(value: Option<f64>) -> Result<Timing, InvalidTiming> {
    let timing = Timing::from_optional_har(value)?;
    Ok(timing)
}
assert_eq!(optional_dns(Some(-2.0)), Err(InvalidTiming));

When conversion returns Ok, ? extracts the timing and execution continues. When conversion returns Err, ? returns that error from optional_dns immediately. The surrounding function must have a compatible error return type.

This small helper exists to make that behaviour visible. The importer uses it in a longer sequence of field checks. Returning an error lets the caller explain the failed field to the user. Calling unwrap would instead panic when the result is Err, which is unsuitable for an expected input failure.

Know where validation applies

The conversion above validates optional numeric timings. The importer must also check JSON types and enforce stricter rules for required durations. For example, a required send duration cannot be absent or -1.

Rust's types enforce the distinctions we have represented, but they do not invent rules we have left out. The public timing variants allow other Rust code to construct values directly. The current guarantee for capture data comes from passing it through the importer before use.

/book/importing-a-har CHAPTER 08

Turning a capture into requests

You open the recording of our book request. The file contains text, but the screen needs a request with a method, a URL, a response, and timings it can interpret. How do we get from one to the other without losing information?

This is the importer's job. It reads the file, checks the fields the application needs, and builds the values the rest of the program will use. The interesting part is deciding what we can accept and what each accepted value means.

Reading structure comes before understanding meaning

JSON can tell us that a field contains a number. It cannot tell us whether that number is a valid HTTP status. A parser reads JSON's structure; validation then applies the capture's rules.

Suppose the file contains "status": 200. Parsing recognises a field named status and the number 200. Validation accepts it as a response status. If the number is 700, the JSON is still readable, but the status is outside the range accepted by our inspector.

The difference matters for errors. A broken JSON document and an invalid field both prevent import, but they fail for different reasons. An error should locate the problem without asking the reader to guess which check failed.

Each step adds understanding. None needs to send a request to the address in the capture; we are examining an existing record.

Keep the original observation

Validation does not give us permission to tidy away inconvenient distinctions. Two headers with the same name remain two headers. An omitted body remains unrecorded. An optional timing of -1 becomes an unavailable timing, while a zero remains a recorded duration.

We also keep the exporter's numbers when they disagree. If the available timing stages do not add up to the reported total, a warning makes that disagreement visible. Replacing the total with our own sum would erase the observation we are trying to investigate.

There is a similar reason to retain timestamp text alongside its parsed value. Two timestamps can use different time-zone offsets while naming the same instant. We compare the instants when sorting, and keep the original text for inspection.

When two recordings describe the same body differently

Suppose a form submits two tags, one called one and another called two. An export may retain the body as text: tag=one&tag=two. Here each equals sign separates a field name from its value, and the ampersand separates the two fields. The repeated name matters: replacing the pair with a single value would lose one tag.

Another export may include a list of those fields as well as the text. The list is convenient for reading, while the text preserves the exporter's spelling. Having both is useful. Rejecting the whole request because it has two descriptions would prevent us from inspecting information the browser deliberately recorded.

Netscope retains each description independently. If the text and fields disagree, it does not silently rewrite either one. Nor does a field list establish the original bytes sent over the connection: file uploads, for example, need separators and file contents that the list may not contain. The inspector shows what was retained and leaves that limit visible.

Rust's enum, introduced in the chapter about missing values, lets us name the possible shapes of this data. A request body can be unrecorded, text alone, fields alone, or both text and fields. Each alternative owns the values it needs. When the inspector borrows the combined alternative, it can read both descriptions without moving either out of the request. Closing the inspector therefore leaves the imported record available for the next visit.

There is a second reason browser recordings can differ: the browser may still be collecting information when the export begins. A response body can appear in a record whose status is still zero or whose protocol label is empty. Zero here means no HTTP status was recorded; it does not tell us that the request failed. Likewise, an omitted response media type means we cannot identify it from that field. A media type is a label such as text/plain that describes how content should be interpreted.

These are specific acceptance rules, not permission to ignore every malformed field. An empty protocol string can represent an unrecorded label; a number in its place remains an error. A missing expiry date for a cookie tells us that the export supplies no date, not how long the browser will keep the cookie. Before accepting a variation, we decide what the reader can safely conclude from it.

Decide when a failure blocks the request

An invalid required wait duration prevents us from accepting that request. A missing optional response body does not. We need a deliberate rule for each field, because accepting a capture and recovering every piece of it are different questions.

Consider a body stored as base64. Base64 represents bytes using a restricted alphabet of text characters. It lets a JSON string carry data that might not be readable text. Decoding reverses that representation.

If decoding succeeds, we check whether the bytes form valid UTF-8 text. Readable text can be displayed as text; other bytes receive a binary preview. If decoding fails, we can still inspect the method, URL, headers, and timings. The body remains stored in its encoded form with an explanation of the failure.

This is a recoverable body warning. In contrast, an invalid required field rejects the capture. These policies determine what the reader sees; the exact acceptance rules live in the input contract.

Build a complete session before displaying it

A session contains the requests loaded from one capture. During import, each accepted request goes into a vector in source order. Ownership moves into that vector, including the request's owned strings and body representation.

If a later required field fails validation, the function returns an error. The temporary vector has not become a usable session, and Rust cleans up its owned values when they leave scope. The application reports the failure instead of showing a partial list as though import had succeeded.

After every entry passes, the session can support a chronological view. A separate list of IDs determines display order, as described in the collection chapter. Sorting the display does not change which entry an ID identifies.

In the implementation, Result expresses whether import produced a session or an error. The ? operator stops a sequence of checks when a required step fails. Those language features make the policy visible in code; the policy comes from what we need the inspector to mean.

Why finish validation before opening the list?

Another design could show valid entries immediately and skip those it cannot read. That could be useful for a damaged file, but the interface would then need to explain what was omitted. A missing redirect candidate might mean no matching request was recorded, or that a matching entry was discarded during import. Without that distinction, partial recovery could look more certain than it is.

Netscope currently builds the complete accepted session before displaying it. That keeps rejection clear, but costs initial waiting and memory. The parser first constructs a tree of JSON values, then builds the request values that the rest of the program uses. A streaming parser could consume entries more gradually; it would need to preserve our duplicate-field checks, useful error paths, and whole-capture acceptance rule. Streaming input and allowing partial results are separate decisions: either can exist without the other.

Put a limit on the work

A local file can still be too large to process comfortably. Netscope limits input bytes, the number of entries, and the amount of decoded body data. Checking during reading also handles a file whose size changes after it is opened.

A body preview has a different purpose. We may retain more information than fits on a screen, so the preview shows a bounded portion and labels any truncation. A preview limit must not make a large captured body look empty or make an incomplete display look complete.

Text adds one more constraint: a UTF-8 character can occupy several bytes. A byte limit may land in the middle of a character. A slice is a borrowed view of part of the existing text. Before taking that slice, the preview moves the boundary back to a complete character. The screen chapter then explains how that text occupies terminal columns.

The particular limits are engineering choices recorded in the contract. Understanding why limits exist is more durable than memorising their current values.

Keeping your place on screen

You select the second request, open its details, and scroll to the response body. When you press Esc, you expect to return to the same request in the list. If the window becomes smaller, you still expect the program to remember what you were inspecting.

Those expectations tell us what the interface needs to remember. The capture itself stays the same while your place within it changes.

Separate the capture from your place in it

The session owns the recorded requests. A smaller set of values records the selected row, the active screen, and the scroll position. Together, these values are the view state: the information needed to decide what to show next.

Opening the inspector changes that state to identify one request. Returning to the overview restores its saved selection and scroll position. We do not need another copy of the captured body to remember either screen.

When the capture is empty, there is no selected request. Rust's Option represents that absence. Pressing Enter can therefore leave the empty view in place instead of attempting to look up a nonexistent row.

Describe the screen with an enum

When browsing requests, we switch between the overview and an inspector for a particular request. Those alternatives fit an enum. In Netscope, they are named Overview and Inspector(RequestId).

The host view introduced in the next chapter adds another screen variant using the same idea.

The parentheses mean that the inspector variant carries a request ID. This keeps the fact that we are inspecting a request together with the identity of that request. A separate true-or-false flag would still need another value to say which request it meant.

The same key can have different meanings in those two states. Down selects the next request in the overview and scrolls one line in the inspector. A match on the current screen and action makes that decision explicit. The result is another state we can inspect in a test.

Borrow data, change selection

Drawing needs read access to the capture. Navigation needs to change the view state. Rust distinguishes those permissions in the references passed to a function.

&Session is a shared reference. It lets the drawing code inspect the session while its owner keeps the data alive. &mut App is a mutable reference to the value holding view state. It permits updates, such as adjusting a scroll offset after a resize.

Here, mut follows the ampersand because it describes the reference's permission. This is related to, but distinct from, writing let mut selected: that earlier example made a local variable changeable. A mutable reference lends change access to an existing value.

Rust checks that this mutable access is exclusive while it is in use. The caller cannot also use a conflicting reference to the same state during that borrow. After drawing returns, the event loop can borrow the state again to apply the next action.

The drawing function also receives a mutable frame. A frame represents the terminal cells being prepared for the current screen. Writing those cells changes the display, while the borrowed capture remains intact.

Move through a list that does not fit

Suppose the capture contains ten thousand requests and the window has room for fifteen rows. Pressing Down thousands of times would keep the rules simple but make the program tedious to use. Page Down moves the selection by the number of rows the current view can display. Home selects the first request; End selects the last. Page Up moves back toward the beginning.

Selection and scrolling still answer different questions. Selection identifies the request you want. The scroll offset identifies the first row visible in the window. After moving the selection, the program adjusts that offset only as far as needed to keep the selected row visible. Near the end, it also avoids leaving an unnecessary blank region below the last request.

A host filter changes the list these movements refer to. If a host has one hundred requests, End selects its hundredth request, even if the complete capture has thousands more. Returning to all requests restores the earlier position in that complete list. The selected row is a position within the current list; its request ID identifies the original captured entry. Keeping those two numbers separate prevents opening the wrong request after filtering.

The inspector uses the same keys to move through wrapped lines rather than requests. Its page size is different because the screen reserves a different amount of space for headings and controls. Resizing changes how many rows fit, so the next page movement uses the new size. An empty list has no selection to move, and a temporarily unusable window preserves the previous position.

There is also an arithmetic boundary to respect. Moving up fifteen rows from row three must stop at the beginning. Rust's unsigned integers represent zero and positive values; they cannot represent a negative row. Saturating subtraction stops at zero instead of producing a negative result. Movement toward the end is bounded by the list's last valid position. These rules make a page key predictable even when less than a full page remains.

A line of text has more than one length

The letter A uses one UTF-8 byte and usually one terminal column. The character 界 uses three UTF-8 bytes and commonly two columns. An accented letter can contain a base character and a combining mark, while a joined emoji may contain several Unicode characters.

These examples explain why counting bytes is not enough to wrap a header. The view needs to keep visible units together and estimate how many columns they occupy. A grapheme is a unit used for that grouping. Netscope walks through graphemes and uses a Unicode width library to count columns before wrapping the line.

Wrapping happens before choosing which lines to display. Otherwise, the scroll position could refer to the original lines while the screen showed a different number of wrapped lines. A long header remains available by scrolling rather than disappearing after its first screen-width portion.

Some captured characters are terminal commands rather than ordinary visible text. ESC can begin a sequence that changes colour or moves the cursor. We turn these controls into visible escaped text before drawing, so inspecting a header cannot make the terminal execute its contents.

Terminal fonts and Unicode versions can still differ. The tests establish how our chosen libraries lay out representative strings; they do not establish identical appearance in every terminal emulator.

Repeat a small loop

The interactive program draws a frame, waits for input, changes the view state, and draws again. Several physical keys can become the same action: j and Down both mean move down. Keeping that conversion separate lets the navigation rules work with actions rather than every keyboard detail.

Ratatui, the terminal drawing library, accepts a closure when it is time to draw. A closure is a function-like value written where it is used. It can borrow values from the surrounding code. Ours uses the session and the current view state to prepare one frame.

We can call the same drawing function with a fixed screen held in memory. A test can then check the visible text, the selected row's styling, and what appears at different sizes. No person has to press a key at exactly the right moment to test those rules.

Leave the terminal usable

An interactive viewer changes how a terminal receives input so keys can be handled without waiting for Enter. It also uses an alternate screen, which gives the viewer a display separate from the shell's usual contents. On exit, those settings need to be restored.

A guard is a value that takes responsibility for cleanup. Our terminal guard records the changes made during setup. Normal exit explicitly restores them. If the function returns early after an error, the guard's Drop implementation attempts cleanup when the guard leaves scope.

Drop is Rust's custom cleanup mechanism. It connects this terminal problem to the ownership rule we first met with String: a value can carry responsibility for releasing a resource. A terminal setting is a different resource from a text buffer, but both need a clear owner for cleanup.

Cleanup can also fail, so the explicit restoration path reports errors. A separate pseudo-terminal check exercises actual terminal settings after both quitting and an injected drawing failure. A pseudo-terminal behaves like a terminal connection under program control; it lets the test inspect mode changes without depending on a person's terminal window.

/book/grouping-requests CHAPTER 10

Seeing a group without losing its requests

The request list is useful when you know which entry to inspect. With hundreds of entries, you may first want a smaller question: how many requests went to the host that serves our book list?

A host summary answers that question by collecting entries with the same URL host. It gives you a way into the capture while keeping the individual records available. The important choices are what makes two entries belong together and what a number about the group actually means.

Choose what makes a group

In https://api.example.test/books, the host is api.example.test. The path identifies /books within that address. Several paths can therefore belong to the same host group.

Netscope uses the normalised host produced while parsing the URL. This lets different letter casing in an ordinary hostname belong to the same group. A different subdomain, such as sub.api.example.test, remains a separate host. Schemes and ports do not divide this particular grouping: an HTTP URL and an HTTPS URL with the same host can appear together.

That rule defines a useful collection of requests. It does not establish that they reached one machine or used one connection. A summary's title needs to name the rule it uses, which is why the screen says it groups by URL host.

Count each entry once

Imagine these three requests in source order: one to api.example.test, one to assets.example.test, and another to api.example.test. To count the API requests, start at zero, read each host, and add one when it matches.

A loop expresses this repeated operation in Rust:

rust · teaching example
let hosts = ["api.example.test", "assets.example.test", "api.example.test"];
let mut api_requests = 0;
for host in hosts {
    if host == "api.example.test" {
        api_requests += 1;
    }
}
assert_eq!(api_requests, 2);

The square brackets create an array, a collection whose length is fixed. All of its elements have the same type; here they are references to quoted text. This short example uses an array because we already know all three names. The imported capture uses a vector so it can hold however many entries the file contains within its limit.

for host in hosts gives the name host to each element in turn. The code inside the braces runs once for each element. We do not need to maintain a separate numeric position to advance through the array.

The if statement runs its body only when the condition is true. == compares the names, while the single = earlier assigned an initial value. The counter is mutable because each matching entry changes it. After the loop, the assertion checks the result.

To produce a summary for every host, the program needs to find the right counter for each name. A map provides that lookup: a key identifies a stored value. Here, the host name identifies its summary. The map helps find a group; the original vector still retains every request, including repeated ones.

Keep missing statuses visible

We can repeat the same counting idea for response statuses. A reported 200 contributes to the 2xx count; a reported 503 contributes to the 5xx count. These are counts of values in the recording.

Status zero needs its own count because HAR uses it when no HTTP status was recorded. Putting those entries into a success count or diagnosing them as a particular network failure would add a conclusion the value does not support.

The selected host also shows how many requests have import warnings. One request with several warnings still contributes one to that count. Defining the unit before counting prevents a small ambiguity from becoming a misleading label.

A sum answers a different question from elapsed time

Suppose two requests to the same host start together. One takes 40 ms and the other takes 60 ms. Adding their reported durations gives 100 ms, but the interval from their common start to the later finish is 60 ms in this invented example.

The horizontal lines below share one time scale. Their overlap is the reason the sum and elapsed interval differ.

The arithmetic itself is straightforward:

rust · teaching example
let reported_durations = [40.0, 60.0];
let mut sum = 0.0;
for duration in reported_durations {
    sum += duration;
}
assert_eq!(sum, 100.0);

This loop correctly adds the durations. The meaning comes from the question we asked it to answer. Calling the result elapsed time would be an error in interpretation, even though the addition is correct.

The host view therefore labels the value as a sum of reported durations and notes that requests can overlap. It adds each entry's reported total once. It does not also add SSL timing, which may already be contained in the total.

Numbers also have a finite representable range. If a sum grows beyond that range, the summary displays Overflow while retaining the requests. It does not display infinity as a measurement or substitute zero. This is another use for the distinction between an available value and an unavailable result.

Filter the view while keeping identity

Selecting a host narrows the request list to that group's IDs. Those IDs still identify their original source entries, and their order still follows the recorded start times. Filtering out other rows does not renumber the remaining requests.

Keeping the request records in one place lets the inspector borrow the same data whether you opened it from the complete list or a host's list. Returning to all requests can also restore the position you had before filtering. The filter changes what you are looking at, not the captured values.

Timing bars retain the complete capture's scale when a host filter is applied. A request therefore does not appear longer merely because you hid requests to other hosts.

Why calculate a group before drawing it?

The captured requests stay unchanged while you browse. We can therefore calculate host counts and ID lists once and reuse them on later screens. This spends memory on the summaries but avoids repeating the same count for every keypress. The lists contain request IDs, so grouping does not make another copy of every response body.

Calculating only when Hosts is first opened would defer that work for readers who never need it. Recounting each time would avoid keeping a summary but repeat the work. If requests arrived continuously, a once-built summary would become stale; we would need to update it or rebuild it. The present choice depends on an offline, unchanging session, not on a rule that caching is always better. A cache is retained information that avoids calculating or fetching the same answer again.

Did the browser follow the redirect?

You ask for /old-books. The server's response says to try /books instead. A little later, the capture contains a request for /books. It is tempting to draw an arrow between them and move on.

Now imagine that two browser tabs were open. One tab followed the instruction; the other asked for the same page independently. Both requests could have the same address and almost the same start time. The recording gives us useful evidence, but the address alone cannot tell us which tab acted on the response.

A good inspector should help you examine that uncertainty. It should also preserve it when the evidence cannot settle the question.

Read the instruction before finding a follow-up

A response header is a named piece of information sent with the response. For a redirect, the Location header gives an address to consider next. It can contain a full URL, such as https://example.test/books, or a relative reference, such as /books. A relative reference needs the original URL to determine the complete address. Resolving /books against https://example.test/old-books gives https://example.test/books. Location in HTTP defines this relationship.

The method also matters. A 307 or 308 redirect preserves it. A 301 or 302 allows POST to become GET. A 303 permits a retrieval with GET or HEAD. Netscope considers those five statuses when suggesting follow-ups. HTTP redirection semantics describes the status rules.

Those fields tell us what the response instructed the client to do. Finding a later compatible request is a separate step. The later request could be absent from the export, or the client could have chosen not to follow the instruction.

Two plausible requests are still two requests

Consider this small invented recording. Each number identifies one entry, and the times are measured from the beginning of this example. The arrows below show possible explanations, not recorded links.

Both later requests satisfy the same basic observations: they ask for the destination using GET, and they start after the redirect response's reported end. Choosing #1 because it appears first would make the display simpler, but it would add a claim that the recording has not established.

Even if #2 were removed, the remaining match would still be a suggestion. Another action could have produced it. A single plausible explanation is useful evidence; it is not automatically a proven cause.

This distinction changes how we read a screen. “One candidate” invites inspection. “Ambiguous” tells us to keep more than one possibility open. Neither label should become “the browser followed this request.”

A search needs a stated boundary

Suppose the same address appears again an hour later. Should it count? Without a boundary, a long capture could connect unrelated activity simply because a URL was reused.

Netscope looks for compatible requests starting no more than 30 seconds after the source's reported end. It also requires a strictly later start than the source and excludes requests beginning before that reported end. These are rules for this tool, not promises made by HTTP. They make the search reproducible: the same recording and rules produce the same candidates without consulting the current time.

There is a cost to this choice. A client might act on response headers before the full response finishes, or follow a redirect after a long pause. Those cases can fall outside our window. “No candidate” therefore tells you about the search result, not whether the browser ever followed the instruction. An inaccurate recorded duration can affect the result too.

An absent Location creates a different problem: there is no target for this search. Several Location headers create uncertainty about the instruction itself. Netscope explains those cases instead of choosing one header or filling in a target from exporter metadata.

Give different outcomes different Rust values

We now have two kinds of absence. Sometimes we cannot search. Sometimes we search and find no candidates. If both become an empty list, the program loses the distinction before it even draws the screen.

Rust lets us describe alternatives with an enum, a type whose value takes one of several named forms. A form can carry its own data. The small teaching example below has an unavailable search and a completed search carrying a vector of request numbers. The production analysis also records the resolved target and explanations, but these two forms are enough to study the distinction.

rust · teaching example
enum Search {
    Unavailable,
    Completed(Vec<usize>),
}

fn candidate_count(search: &Search) -> Option<usize> {
    match search {
        Search::Unavailable => None,
        Search::Completed(ids) => Some(ids.len()),
    }
}

let unavailable = Search::Unavailable;
let no_matches = Search::Completed(vec![]);
let ambiguous = Search::Completed(vec![1, 2]);

assert_eq!(candidate_count(&unavailable), None);
assert_eq!(candidate_count(&no_matches), Some(0));
assert_eq!(candidate_count(&ambiguous), Some(2));

Completed(Vec<usize>) means that this form contains a vector of unsigned whole numbers. Here they stand for request IDs. The parentheses in Search::Completed(vec![1, 2]) put a particular vector into that form. The double colon selects a name belonging to the enum, just as it did in the earlier missing-value examples.

The function receives &Search, a shared reference. It can inspect the search while the caller keeps ownership. match examines which form is present and runs the corresponding arm, the expression after =>. In the completed arm, ids borrows the vector inside the search; Rust does not move that vector out through the shared reference. Calling .len() reads its number of elements.

The returned Option<usize> carries the distinction further. None says there is no count because the search was unavailable. Some(0) is a count from a completed search. The assert_eq! checks compare each actual result with the expected value; a mismatch fails the example when it runs. Predict those three results before looking back at the function.

This is why the choice of a type matters to the explanation on screen. Keeping the alternatives distinct gives the display enough information to tell the truth. It does not, by itself, prove that our matching rules are good; those need their own review and tests.

      └ · · possible repeat · · → #2 GET /books · start 30 ms

Known: the recorded requests share the compared fields.
Unknown: whether either request was caused by the earlier error.

It would be misleading to call #1 “attempt two” and #2 “attempt three.” That numbering assumes they belong to one sequence of attempts. A capture may contain both a retry and an independent request, and these fields do not identify which is which.

The same caution applies to a later response. A candidate that receives status 200 has a recorded response outcome, but that alone does not establish that it repaired the earlier failure or completed the user's task. Netscope shows possible repeats without giving them a success label.

An address is only part of a request

Two requests can ask for the same URL while carrying different information. One might include a cookie identifying a signed-in session; another might have no such cookie. A header might ask for a different representation. A body might contain different submitted data. Looking only at the address would hide these differences.

Our first retry analysis therefore uses a narrow comparison. It considers GET and HEAD, requires the exporter to report a request body size of zero with no captured body representation, and compares the recorded request headers, query fields, and cookies exactly. It also compares the method and the normalized URL. The redirect lesson introduces why an address may need normalization before comparison.

“Exactly” has a consequence here. Reordering the captured headers excludes a candidate, even if that order would make no practical difference to the server. A changing request identifier could also exclude a real retry. This policy favours a clear, reproducible comparison over an attempt to guess which differences the application considers meaningful.

Missing body information is a separate problem. No captured body text does not prove that the request had no body. Requiring a reported zero size adds evidence, but it still relies on the exporter. Similarly, two empty header lists can compare equal even if both exports omitted information. Equality applies to the values we have.

Turn a comparison into a Boolean value

Rust represents a yes-or-no answer with bool. Its two values are true and false. The equality operator, ==, compares two values and produces a Boolean. It is different from the single = used to assign a value to a variable.

The example below compares just methods and ordered header lists. It deliberately leaves out the other application rules so we can follow each result. A header is represented here as a pair of text values, its name and value. Rust calls a fixed group written in parentheses a tuple. Unlike a vector, a tuple has a fixed number of positions, and those positions can have different types; these two both happen to contain borrowed text.

rust · teaching example
let earlier_method = "GET";
let later_method = "GET";
let earlier_headers = vec![("Accept", "application/json"), ("X-View", "books")];
let later_headers = vec![("Accept", "application/json"), ("X-View", "books")];

let same_method = earlier_method == later_method;
let same_headers = earlier_headers == later_headers;
let same_recorded_fields = same_method && same_headers;
assert_eq!(same_recorded_fields, true);

let reordered_headers = vec![("X-View", "books"), ("Accept", "application/json")];
assert_eq!(earlier_headers == reordered_headers, false);
assert_eq!(earlier_method == "HEAD", false);

// Comparison leaves both vectors available to their owners.
assert_eq!(earlier_headers.len(), 2);
assert_eq!(later_headers.len(), 2);

Vector equality first requires equal lengths and then equal elements in corresponding positions. Each tuple compares its corresponding fields. The first pair of vectors has matching values at every position, so the result is true. In the reordered vector, the first element is different. Having the same two headers somewhere in the list is not enough for this comparison.

The && operator means “and”: both conditions must be true. Rust evaluates the expression on its left first. If that expression is false, the whole result must be false, so Rust skips evaluating the expression on the right. This behaviour is called short-circuit evaluation. In our example, the two comparisons have already been stored in variables; combining them merely reads those Boolean values.

The comparisons do not transfer ownership of the vectors. Rust's equality operation borrows the values for comparison, which is why both vectors remain usable afterward. The final checks read their lengths. A comparison can inspect owned data without consuming it.

Notice what the name same_recorded_fields says. It describes the result of these comparisons. Naming it was_a_retry would make a stronger claim without adding any evidence. Good names help the next reader understand the limit of a value.

Decide when to look for a repeat

A repeated successful request is common during ordinary browsing. Netscope begins this search only after selected recorded error statuses: 408, 429, 500, 502, 503, and 504. This is the tool's current scope, not a universal rule about which operations should be retried. Status zero means that no status was recorded; it does not establish a network failure.

Candidates must begin after the source's start and within the interval from its reported end through 30 seconds later. This bound can exclude real repeats. It makes the search finite and predictable, but does not reveal the application's waiting policy. As with redirects, no matches means only that nothing met the stated rules.

A response may provide Retry-After to indicate a waiting period; 429 is one example where it can appear. Netscope retains that header for inspection but does not interpret it in this analysis. A candidate inside our window is therefore not a claim that the client followed the server's waiting instruction. The definition of 429 explains the header's role in that response.

Recognising a possible past retry is also different from deciding whether to send a request again. HTTP's term idempotent concerns whether repeating an identical request has the same intended server effect as sending it once; it does not promise identical responses. The HTTP method rules matter when designing a client that actually repeats operations. This inspector only reads a recording.

What does HTTP/2 tell us?

Two requests for books overlap on the timeline. Both carry the label HTTP/2. Does that mean they shared one connection? Did the browser send parts of both responses at the same time? Would HTTP/3 have made them faster?

The version label gives us a useful starting point, but those questions ask for more than a name. We need to separate the rules a protocol supports from the events this recording actually contains. Once that distinction is clear, we can decide how to recognize labels in Rust without silently inventing an answer.

A message and the way it travels

An HTTP request expresses an operation, such as GET, on a resource. Its headers provide additional information, and it may carry a body. A response supplies a status, headers, and possibly a body. Those ideas remain useful across HTTP versions.

A protocol also needs a way to represent those messages as bytes. HTTP/1.1 uses a textual opening line and headers, followed by an optional body. A textual header does not require a textual body: an image can still be sent as binary data. The HTTP/1.1 message format specifies that arrangement.

The transport is the mechanism that carries those bytes between endpoints. For HTTP/2, that transport is TCP, which delivers an ordered byte stream. HTTP/2 divides information into frames, bounded pieces with their own control information. Streams identify exchanges within a connection, allowing frames from different exchanges to be interleaved. This sharing is called multiplexing. The HTTP/2 overview describes the design.

The drawing below shows only the idea of interleaving. A and B stand for two exchanges, and each box stands for a piece associated with one of them. The boxes do not represent measured packets, exact frame sizes, or captured timing.

Illustrative diagram

Exchange B:           [B1]             [B2]

One connection: [A1] → [B1] → [A2] → [B2]

A version label says this arrangement is supported.
It does not say this arrangement occurred in our capture.

HTTP/3 carries HTTP over QUIC, a transport with streams. Its rules differ from HTTP/2's use of TCP; changing the transport does not change the basic purpose of GET or a response status. The HTTP/3 overview introduces that mapping.

The important question for this inspector comes next: which of these details did the exporter retain?

A capability is not a measurement

Our imported HAR fields describe requests, responses, and reported timings. They do not contain a trace of the individual frames drawn above. They also do not give us the stream identifiers needed to reconstruct that picture. If two requests overlap, they could have used separate connections. The overlap alone does not settle it.

Similarly, a small reported header size is not enough to measure compression savings. To claim savings, we would need suitable evidence about both the encoded representation and the baseline we compare it with. A number without that context cannot supply the missing comparison.

A version label also does not tell us how much faster another protocol would have been. That comparison needs an experiment with controlled conditions or additional measurements. Netscope therefore presents general protocol notes beside the recorded labels, with an explicit boundary between the two.

This does not make the label useless. It gives us a vocabulary for asking the next question. We can ask for a connection trace, look for missing exporter fields, or design a separate experiment. We simply avoid presenting the answer before we have that evidence.

Why the body can be larger than the download

Imagine downloading a book description with a sentence repeated many times. Compression represents repeated content more compactly; decompression restores the original bytes. Gzip and Brotli are two compression formats a server can use for a response body. They are separate from the way HTTP/2 represents headers and divides messages into frames.

The browser can decompress a response before saving its content in a HAR. The captured headers still describe the response that arrived, so Content-Encoding: gzip may appear beside ordinary readable text. Applying gzip decompression to that text again would be a mistake: the browser has already performed that step.

When a connection timing is not a measurement

Now suppose a later request has a connection timing of -1. This is the exporter's marker for an unavailable duration. It is not a measured duration of zero. If the field is omitted entirely, the record supplies no value at all. A numeric zero remains a reported zero; its precision and collection rules do not establish that no work happened.

Rust's Timing enum keeps these cases separate. An enum value selects one named alternative: missing, unavailable, or a duration carrying a number. The inspector matches that alternative to choose the display. It can show an unavailable label without manufacturing a number that would later enter a calculation.

Reusing a connection could explain why a later request has no new connection setup measurement, but the timing field alone cannot prove reuse. Even a reported zero is insufficient. We need separate evidence about which connection handled each request. The browser compatibility reference keeps our controlled server observations separate from what the HAR inspector can infer.

Keep both labels when they differ

The file has one protocol field on the request and another on the response. If one says HTTP/1.1 and the other says HTTP/3, choosing the newer value would throw away the disagreement. Calling it an upgrade would add a story that these two strings do not establish.

Netscope shows both originals, recognizes each independently, and labels disagreement. It also accepts unrecognized nonempty text as captured data. A label such as HTTP/4 stays visible even though this version of the inspector does not explain it. “Unrecognized” describes our recognition policy; it does not declare that the exporter is wrong.

Sometimes different strings have the same classification. Netscope explicitly recognizes HTTP/2, HTTP/2.0, http/2.0, and h2 as HTTP/2 labels, and similarly recognizes three documented spellings for HTTP/3. Those are supported spellings in this tool, not permission to treat any text beginning with “HTTP/2” as the same value.

Read text without taking ownership of it

The recognition function needs to look at a label, but it does not need to own or modify the text. Rust's &str is a shared reference to a string slice: a view of UTF-8 text whose bytes are kept alive elsewhere. A String, by contrast, owns a text buffer that can grow. We met that ownership in the storage chapter.

Here is a small recognizer for the supported HTTP/2 spellings. It returns a Boolean, the true-or-false value from the previous chapter. The full application keeps a separate classification for each recognized version and for unrecognized labels.

rust · teaching example
fn is_http2(label: &str) -> bool {
    match label {
        "HTTP/2" | "HTTP/2.0" | "http/2.0" | "h2" => true,
        _ => false,
    }
}

let captured = String::from("h2");
let recognized = is_http2(captured.as_str());
assert_eq!(recognized, true);
assert_eq!(captured, "h2");
assert_eq!(is_http2("HTTP/20"), false);
assert_eq!(is_http2("HTTP/2 "), false);

captured.as_str() lends a view of the existing string to the function. It does not copy the buffer or transfer its ownership. The caller can still read captured afterward. The borrowed view is valid while the owning string remains alive, and Rust checks that borrowed access does not outlast its data.

Inside match, each quoted value is an exact text pattern. The vertical bar, |, separates alternative patterns in the same arm: any of those four spellings produces true. It is not the Boolean && operator from the previous lesson. The underscore, _, accepts every value left over and produces false. That final arm also handles future labels the author has never seen.

The last two checks are deliberate. HTTP/20 shares a prefix with HTTP/2, but exact matching does not confuse them. The trailing space in the final example is part of the string, so that spelling does not match either. We could choose a different recognition policy later, but it should be an explicit change rather than an accidental consequence of a broad comparison.

How can we change a request without changing the recording?

You find a GET request for a list of books and want to try it against a server on your own machine. The recorded address is useful as a starting point, but it is also evidence of what happened earlier. Editing that evidence would make the capture harder to trust.

We need two things to exist at once: the original request and a separate draft we can change. Before sending anything, we also need a way to examine what those changes mean. A mistyped address should remain editable, and a header chosen for one destination should not quietly travel to another.

Opening a review prepares a possible action. It does not perform that action. Only an explicit Send starts the new request. This chapter follows the data up to that boundary; the next chapter explains what happens while we wait for an answer.

Give the draft its own text

A draft begins as a copy of selected information. It does not need another copy of the entire capture, its response bodies, or every timing. It needs its own URL text, header choices, and the identity of the request it came from.

We previously saw that assigning a String to a new variable moves ownership. A move would leave the original variable unable to use that String. Here, both the capture and the draft must remain usable independently, so the draft needs a copy of the text. Rust's clone() method makes that copy for a String.

The diagram shows ownership, not a precise memory layout. Each arrow points to text owned by that value. The two buffers initially contain equal text, but changing the second one does not change the first.

rust · teaching example
let captured_url = String::from("https://example.test/books");
let mut draft_url = captured_url.clone();

draft_url.clear();
draft_url.push_str("http://localhost:8080/books");

assert_eq!(captured_url, "https://example.test/books");
assert_eq!(draft_url, "http://localhost:8080/books");

mut allows the draft variable to be changed. clear() removes the string's contents, while push_str() appends borrowed text to it. These methods operate on the draft's buffer. Neither requires changing the captured string.

Cloning has a cost: it creates independently owned storage and copies the text bytes. That cost is justified here by the behaviour we want. Cloning every response in the capture would spend memory without helping us edit this URL. Choosing what to copy is part of designing the feature, not just satisfying the compiler.

Invalid text still belongs in an editor

While replacing an address, you might temporarily have just http: in the field. Rejecting every keystroke until the entire address is valid would make ordinary editing difficult. Instead, the editor keeps the draft text and explains why it cannot yet be reviewed.

There are two different questions: “What has the user typed?” and “Is that a supported destination?” Keeping them separate lets you repair the text without losing it. Netscope checks for a complete HTTP or HTTPS URL with a host and rejects embedded credentials, controls, whitespace, and backslashes. It also places a size limit on editable text.

Once the address is valid, the review shows the effective destination produced by parsing it. For example, a default port or a path containing .. can have a simpler serialized form. A fragment, the part after #, is disclosed separately because it is not included in the HTTP request destination. The original text remains in the draft so you can return and edit it.

These are validation rules for this editor. They are not evidence that the server exists or is reachable. No connection is attempted while validating a draft.

A destination change also changes a decision

Suppose you explicitly select an Authorization header for one destination, then change the URL to a local server. Keeping that header selected would carry a choice into a different context. Netscope therefore clears the request body and selected or manually added headers whenever the saved URL text changes, and immediately explains the reset.

Every draft starts with no captured headers selected. Repeated captured headers remain separate choices. Fields managed by the HTTP client, such as Host, Content-Type, and Content-Length, cannot be copied as ordinary user headers. A blocked entry includes its reason, so a disabled choice does not look like a broken key.

All header values are hidden in the draft list and review until you explicitly reveal them. Masking every value avoids guessing which custom header might contain private information. Names remain visible so you can navigate. When you enter a new value, the editing field shows what you type; leaving that field restores masking.

These choices describe the request we intend to prepare. They do not recreate a browser's cookie storage or login state, and they do not make the draft identical to the original request.

Review the current draft, not an earlier one

A review is a freshly validated view of the current draft. It names the source request, shows the effective destination and selected headers, and distinguishes fields managed by the client. It also states the timeout and response-size limit.

Returning to edit leaves the review. You must review again after changing the draft; there is no old approval carried into a new destination. Only Enter or s from a valid review starts sending. Opening the review itself does no network work.

This separation matters during sending. A draft can change while someone is preparing it. An accepted operation needs a definite set of values to work with. The next chapter follows that operation through waiting and cancellation.

/book/waiting-for-a-response CHAPTER 15

How can we wait for a server and still respond to a key?

You review a request to a server on your own machine and press Send. The server receives it, but sends nothing back. You press Esc. The application should notice that key even though the response has not arrived.

This is a different problem from reading a completed capture. A capture gives us values we can examine immediately. A live request has intervals when there is no answer yet. During those intervals, the application must keep track of unfinished work, remain able to accept input, and decide what to keep if waiting ends early.

Waiting does not need to occupy the terminal

A thread is a sequence of instructions that the operating system can schedule independently of another sequence. Netscope keeps terminal input on one thread and gives a send operation its own worker thread. Waiting for a server therefore does not require the terminal thread to stop reading keys.

Moving work to a thread is only part of the answer. A worker that waits indefinitely for a response would still need a way to notice cancellation. Our worker uses asynchronous I/O: an operation can report that it cannot progress yet, allowing other pending work, such as a cancellation signal or a deadline, to be checked.

The following timeline is illustrative. Columns represent responsibilities, not processor cores or measured durations. Read downward to follow events. The arrows show information passing between the terminal and the worker.

Illustrative diagram
Terminal                         Worker                       Server
Review → Send ──request values──→ Open connection
Read keys                        Send GET ───────────────────→ Receive request
Draw waiting view                Wait for response             Work continues
Esc ───────────cancel signal───→ Stop exchange
                                 Close connection
Draft ←────────result────────── Keep received data

The terminal does not wait inside the operation that reads the response. It periodically checks for a result and continues reading input. The worker does not keep a reference to an editable text field; it owns the reviewed values for this send. Returning to a draft cannot silently change an operation already in progress.

A future holds unfinished work

Rust calls a value representing an asynchronous computation a future. A future can contain the data and progress needed to continue later. Calling an async fn creates such a value. It does not, by itself, run the function's body.

This small example makes that distinction visible. It creates work and then discards it before anything drives it forward.

rust · teaching example
async fn report() {
    println!("response received");
}

let unfinished = report();
drop(unfinished);

This prints nothing. async changes the kind of function call: the call produces a future whose eventual output would be (), Rust's value for “no useful returned value.” The standard drop function consumes a value and destroys it now. Here it destroys a future whose body has never started.

A future makes progress when it is polled. Polling means asking it to do the work it can do now. It answers either Ready, with its result, or Pending, meaning it needs another opportunity later. A network future can register a waker before returning Pending. A waker is a way for the waiting infrastructure to notify the task when another poll may make progress; it does not contain the response itself.

We do not write a loop that repeatedly asks an idle socket whether a byte has arrived. A runtime coordinates these polls with notifications from the operating system and with timers. Netscope uses the Tokio runtime in the worker. A pending socket read lets that runtime wait efficiently while still being able to wake for cancellation or a deadline.

Awaiting keeps a place to continue

The .await expression lets one future wait for another. If the inner future is ready, execution continues with its output. If it is pending, the enclosing future can also return Pending, keeping enough state to resume at this point later. Values needed after the wait remain part of that state.

Here is a complete, deliberately small example. There is no server in this example: the inner future is immediately ready, so the wait need not suspend at all.

rust · teaching example
async fn received_length() -> usize {
    5
}

async fn describe_response() -> String {
    let length = received_length().await;
    format!("received {length} bytes")
}

fn main() -> Result<(), std::io::Error> {
    let runtime = tokio::runtime::Builder::new_current_thread()
        .enable_all()
        .build()?;
    let description = runtime.block_on(describe_response());
    assert_eq!(description, "received 5 bytes");
    Ok(())
}

usize is an unsigned integer type used for lengths and indexes. The arrow after a function's parameter list names its output type. Inside the asynchronous function, .await turns the inner future's eventual output into the number assigned to length. The format! macro builds a String from the text and the value in braces.

The lower half supplies the machinery that runs the example. The double colons in tokio::runtime::Builder follow names through a library and its modules to a type. new_current_thread() begins a runtime configuration that polls tasks on the calling thread. enable_all() enables its available I/O and timer support, and build() constructs it. Building can fail, so ? returns that error from main, as we saw in the error-handling chapter.

block_on drives a future to completion and returns its output. It occupies the calling thread until that future finishes. This is why Netscope calls it on the worker thread rather than the terminal thread. Inside that runtime, asynchronous waits still allow the response, cancellation, and timer to compete for progress. The example checks the resulting text with assert_eq!; changing the inner return value to 8 would make that assertion fail.

Adding async does not automatically create a thread or make every instruction interruptible. A long calculation that never yields can occupy the thread polling it. Asynchronous code stays responsive when its work between suspension points is bounded and its waits cooperate with the runtime.

Keep one deadline for the whole request

Suppose a server sends a few bytes just before each timeout would expire. If every received chunk started a fresh timeout, that server could keep the request alive indefinitely. Netscope instead records one deadline when Send is accepted. Looking up the host, opening the connection, verifying HTTPS, and receiving the body all spend time from the same allowance.

An operation ends with one accepted outcome. Completion means the HTTP body ended normally; a status such as 404 can still be a complete response. Timeout, cancellation, size limit, and a transport failure explain different reasons why the operation stopped. A transport failure means the connection or HTTP processing failed, rather than that the server chose an error status.

The body limit introduces another boundary. Receiving exactly the allowed number of bytes does not always tell us whether the body is complete. If the HTTP framing says the body has ended, it is complete. If another byte arrives, it is size-limited. If neither fact becomes available before the deadline, it is timed out with the bytes already received.

That distinction matters when examining partial data. “We retained these bytes” and “this is the whole response” are separate claims.

Why keep a separate worker at all?

We could make the entire terminal program asynchronous and run input, drawing, and network operations on one long-lived runtime. That could avoid creating a thread and runtime for each send. It would also move cancellation, terminal input, and shutdown into a different coordination scheme. Asynchronous I/O does not by itself require an extra operating-system thread.

The current design keeps the existing terminal loop in charge of input and gives each send a bounded lifetime elsewhere. This is a choice about separation of responsibilities, not evidence that one thread per operation is always faster. It has setup cost, and waiting for worker cleanup on exit can still occupy the terminal thread briefly. Many concurrent sends would be a reason to reconsider it. The sharing chapter compares handing over a result with sharing a mutable buffer.

Why let a library interpret HTTP?

A response can arrive in pieces that do not line up with a header or body boundary. Handling those pieces correctly is separate from deciding how much data Netscope should retain. Hyper, our HTTP library, interprets the protocol; the application sets its limits and decides what the result means. Rustls handles the encrypted connection and certificate checks for HTTPS, while Tokio coordinates waiting.

Writing our own HTTP parser would add another large correctness problem to a learning inspector. A higher-level client library could do more of the connection management for us, but we would need to check its redirect, retry, cookie, proxy, and decompression behaviour against the reviewed-send promise. Such libraries can be configured; they are not inherently unsuitable. Our current lower-level connection API makes the one-connection lifetime explicit, at the cost of more code to manage it.

The resulting replay deliberately differs from a browser: it sends one reviewed operation using HTTP/1.1, does not follow a redirect or retry an HTTP request, and keeps the received body without automatic decompression. Seeing HTTP/2 in an imported recording does not change that replay capability. The transport decision states the exact limits, and the architecture audit records the alternative assessment without claiming a client-library benchmark.

Cancellation follows ownership

Imagine that the worker has copied three response bytes into its result when you cancel. We want to stop waiting without throwing those three bytes away. The value collecting the result therefore lives outside the future performing the exchange. The exchange borrows it while receiving data. Dropping that future ends the borrow, leaving the collected data available to return.

Dropping a future is a local action. It does not rewind instructions already run. If the server received the GET, it may continue working after we close our connection. It has no access to the draft and cannot deliver a later result into the interface.

The worker returns its result through a channel, a communication path that transfers a value between threads. This channel has room for one result. The body stays with the worker while receiving, then moves with that result; it is not repeatedly copied into a queue of screen updates.

A late result must not change a newer decision

Two events can occur close together: a response finishes and you press Esc. We need an explicit rule, rather than whichever label happens to be drawn last. If the terminal has already accepted completion, a later cancellation does not turn it into a cancelled request. Inside the worker, if cancellation and completion become ready in the same check, cancellation takes priority.

Each accepted send also receives an operation ID, a number that increases for each operation. The terminal accepts a result only while waiting for that ID, and accepts a terminal result only once. An old event therefore cannot replace the outcome of a newer operation. This identity is different from the source request ID: several new operations can all begin from the same recorded request.

While cancellation is pending, editing remains suspended. Once the worker has disposed of the connection and returned, Esc's cancellation path returns to the draft. The retained result is still available through o. It remains a new request's result; it never replaces the captured response.

Who is allowed to change this value?

A response is arriving while you look at the terminal. The network code receives another block of bytes, and the screen wants to show what has arrived. Could both parts of the program simply use the same growing body?

They could, but then we would need rules about when each part may read or change it. Netscope currently chooses a different arrangement: the worker owns the body while receiving it and passes the result back when the operation ends. Before choosing a lock or an atomic variable, we should ask whether two parts of the program need to change the same value at all.

The waiting chapter introduced threads and cancellation. Here we compare the ways those threads could cooperate. Some examples describe alternatives to Netscope's current design; they are labelled where they appear.

Hand the value over when responsibility changes

Suppose the response contains three bytes when you cancel. The worker already owns those bytes. It can finish cleanup and send a result containing them to the terminal. The terminal then owns the result it displays. There is no period in which both threads need to edit that result together.

A channel provides the handoff. Its sender puts a value into the channel; its receiver takes that value out. Netscope uses a result channel with room for one value because each operation produces one final outcome. Cancellation has a separate channel carrying a signal in the other direction.

Read the diagram as a transfer of responsibility. It describes the current design, without implying a particular operating-system schedule.

Illustrative diagram
Terminal thread                         Worker thread
owns editable draft                     owns reviewed request and response bytes
       │                                         │
       ├──────── cancellation signal ───────────►│
       │                                         ├─ stop exchange and close socket
       │◄──────── owned result ──────────────────┤
       └─ owns result for display

The result body moves with the result; sending does not require making a second copy of its entire buffer. The channel coordinates the transfer so the receiver can use the value when it receives it. This does not mean channels have no internal synchronization. It means the application does not have to coordinate simultaneous edits to that body. See Rust's message-passing explanation.

The cost is visible: Netscope does not show a live body growing byte by byte. If we add that feature, we will need another decision. Sending periodic snapshots copies data. Sending chunks needs a bounded queue and a rule for what happens when rendering is slower than receiving. Sharing a buffer needs coordinated access. A channel is appropriate for today's one-result handoff, not automatically the best answer to every future update.

Share lifetime only when lifetime is the problem

Sometimes several values need to keep the same configuration alive without changing it. Rust's Arc<T> is a shared owner for a value of type T. Cloning an Arc creates another owner of the same allocation; it does not clone the contained configuration. The contained value is dropped after the last strong owner goes away.

The name means atomically reference-counted: its ownership count can be updated safely across threads. That protects the count, not arbitrary edits to the contained value. Wrapping a growing response body in Arc alone would not let one thread mutate it while another reads it. Netscope uses Arc for its TLS configuration because the TLS connector accepts shared ownership of that configuration. It is not a shared mutable response store. The Arc documentation explains this distinction.

For a value that never needs shared ownership, an ordinary owner and temporary borrows are easier to follow. For a draft that must change independently, copying the needed text is appropriate. Shared ownership, borrowed access, and independent copies solve different lifetime questions.

Protect several related changes together

Imagine a future progress display with two fields: a byte count and the buffer containing those bytes. Its rule is that the count equals the buffer length. A reader must not see the new count with the old buffer.

A mutex, short for mutual exclusion, can protect the pair. Code acquires the mutex before accessing the pair. While one thread holds that access, another trying to acquire it must wait. The writer can update both fields before allowing another reader in. The protected interval is often called a critical section.

Rust represents that access with a guard. Dropping the guard releases the lock. The Mutex API also reports poisoning: a thread may have panicked while holding the lock, leaving an application rule unfinished. Recovery needs to consider the data's meaning rather than simply ignore that signal.

The design still needs judgment. Holding this lock while waiting for the next network byte could keep the screen waiting too. Two threads that each hold one lock while waiting for the other's lock can become stuck permanently; that is a deadlock. Rust's borrowing checks do not prove that a locking design will always make progress. The Rust book discusses these costs in shared-state concurrency.

For our current final-result display, sharing a mutable body would introduce that coordination without a user-visible need. For a future shared cache with several related fields, a short, carefully scoped lock might be the clearest solution. “Avoid locks” is not a sufficient design rule; first identify the consistency rule the lock would protect.

Update one counter without losing an increment

Consider two callers asking for the next operation number. A separate read followed by a separate write is not enough coordination. Both could read 7, both compute 8, and both believe they reserved the same number.

An atomic operation makes its change indivisible with respect to other atomic operations on that value. An atomic read-modify-write operation reads a value, changes it, and returns a result as one operation. Here is an isolated example of the increment used by Netscope. The example runs sequentially so its result is repeatable; it is not a stress test of competing threads.

rust · teaching example
use std::sync::atomic::{AtomicU64, Ordering};

let next = AtomicU64::new(7);
let first = next.fetch_add(1, Ordering::Relaxed);
let second = next.fetch_add(1, Ordering::Relaxed);
assert_eq!(first, 7);
assert_eq!(second, 8);

use brings these library names into scope. AtomicU64 holds an unsigned 64-bit integer with atomic access methods. new(7) starts it at 7. The fetch_add method adds its first argument and returns the value from before the addition. The example therefore reserves 7 and then 8. The variable binding does not need mut: this type provides controlled changes through its atomic methods. The atomic integer API specifies the return value and overflow behaviour.

Memory ordering answers a separate question: what does this operation establish about access to other memory? Relaxed keeps the counter operation atomic but does not use it to publish unrelated request or response data. Acquiring a new number therefore does not prove that another thread's response body is ready. The response travels through the channel, which supplies its own coordination. See the ordering definitions.

If an atomic flag were instead used to announce that other shared data was ready, Relaxed alone would not establish the needed ordering. Release and Acquire can form such a relationship when an acquiring read observes the releasing write. That relationship still needs a correct ownership and access design for the other data. Stronger ordering on a counter does not automatically make a mutable buffer safe to share.

Netscope's counter is a static: one value with a lifetime spanning the process, shared across editor instances. It labels sends so a completion can be checked against the active operation. It does not identify a saved request across program runs. Atomic addition also wraps after the integer's maximum value, so the implementation does not provide unlimited unique numbers.

Does the current UI require an atomic here? No demonstrated requirement says it does. The terminal currently allocates send IDs on one thread and keeps only one worker active. An ordinary counter owned by the application could make that ownership clearer. It would need to survive replacing an editor and define what happens at its maximum value. The architecture audit records this as an open simplification, not a historical justification for the global counter.

Change a value only if the assumption still holds

Now imagine two callers trying to claim a single unused slot. Each needs to say, “Set it to occupied, but only if it is still empty.” This is compare-and-swap, commonly abbreviated CAS. It is an atomic operation rather than a third category beside atomics and locks.

Rust calls the operation compare_exchange. This illustrative example claims a Boolean slot once. A Boolean holds either false or true; it does not carry a response body.

rust · teaching example
use std::sync::atomic::{AtomicBool, Ordering};

let occupied = AtomicBool::new(false);
let first = occupied.compare_exchange(
    false, true, Ordering::Relaxed, Ordering::Relaxed,
);
let second = occupied.compare_exchange(
    false, true, Ordering::Relaxed, Ordering::Relaxed,
);
assert_eq!(first, Ok(false));
assert_eq!(second, Err(true));

The first argument is the expected value; the second is the replacement. The last two arguments specify ordering on success and failure. Both are relaxed here because the Boolean itself is the entire information being coordinated. A successful call returns Ok with the previous value. A failed comparison returns Err with the value it observed and leaves the slot unchanged. The first call claims it; the second discovers that its assumption is no longer true.

This example never releases the slot. If a real design allowed a value to change away and then back, comparing its current value would not reveal that intervening history. Retrying a failed comparison also needs care: a failed attempt must not have already performed an irreversible action such as sending a request. The atomic Boolean API describes the operation's exact contract.

Netscope does not use application-level CAS to resolve cancellation. The worker already chooses among completion, cancellation, and deadline in one asynchronous selection, and the terminal accepts one result. Adding a second competition through an atomic flag would need a reason and a clearly defined authority. Nor does an ID increment need a handwritten CAS retry loop: fetch_add already expresses the required operation.

Choose from the data relationship

For a single UI owner changing a selection, use an ordinary value. For a worker handing over a finished result, a channel expresses the transfer. For several owners keeping unchanged configuration alive, shared ownership may fit. For related shared changes that must be seen together, consider a lock. For one independently meaningful shared counter or conditional flag, consider an atomic operation.

These choices can coexist in one program. None is a universal performance ranking. The question is which rule must remain true, who can change the data, and what another part of the program may conclude when it reads it.

What does it mean for two responses to match?

The capture shows status 200 and a body containing catalog. Your new request also receives status 200, but the connection stops after cat. The three received letters agree with the beginning of the capture. Calling the responses identical would still be wrong: the new operation did not reach the end of its body.

A useful comparison tells us what agrees, what differs, and what remains unknown. These are different answers. The job is to preserve those distinctions as we move from a screen full of values to a conclusion about them.

Establish which observations are beside each other

The left column belongs to the recorded request. The right column belongs to a new operation whose destination and headers you chose in the draft. An unchanged source request ID connects the two observations, but does not make their conditions identical. You may have replaced a public address with a local one, omitted a header, or sent the request after the server's data changed.

Netscope therefore begins the comparison with both methods, destinations, and status values. The recorded duration and the new elapsed duration have separate labels. A smaller number on the right is something you can observe, but the two numbers alone do not establish why it is smaller. This comparison does not calculate a speedup or attribute a change to a protocol.

A status can be compared only when both observations contain one. In a HAR recording, zero means no status was recorded. A replay that fails before receiving headers also has no status to compare. Neither is an HTTP response with status zero, and neither should be quietly converted to a successful empty response.

Absence is different from emptiness

A captured body can be missing even when the capture includes a status and a reported size. That tells us something about what was recorded, not that the server sent no bytes. By contrast, an explicitly stored empty body gives us a representation with length zero.

The diagram separates these cases. Each box describes retained data, and the arrow names a conclusion that those data support. No arrow reconstructs anything the exporter omitted.

Ask a smaller question about a partial body

A prefix is the beginning of a sequence. The common comparison region is as long as the shorter available sequence. If one side contains three bytes and the other contains seven, there are three positions at which both sides have a byte.

We can ask whether those positions agree without claiming anything about the remaining four. If the overlapping bytes differ, we can report the first differing position. If no bytes overlap, there is no prefix evidence to compare. The outcome that stopped the replay stays visible beside this narrower conclusion.

Rust lets a function inspect this region through a slice. A slice is a view of consecutive elements owned elsewhere. &[u8] means a shared reference to a slice of bytes: u8 is an unsigned integer with values from 0 through 255. The function can read the bytes without making another body-sized allocation or taking ownership of either body.

This small example answers only the prefix question. It deliberately leaves out response status, encoding, and completion; those are separate reasons the application may decline a body comparison.

rust · teaching example
fn shared_prefix_matches(left: &[u8], right: &[u8]) -> Option<bool> {
    let shared = left.len().min(right.len());
    if shared == 0 {
        return None;
    }
    Some(left[..shared] == right[..shared])
}

fn main() {
    assert_eq!(shared_prefix_matches(b"catalog", b"cat"), Some(true));
    assert_eq!(shared_prefix_matches(b"catalog", b"car"), Some(false));
    assert_eq!(shared_prefix_matches(b"catalog", b""), None);
}

The main function runs three checks on the helper function. The b before a quoted ASCII string makes a byte string, so the example compares bytes rather than doing text-aware matching. len() gives each slice's length, and min() chooses the smaller number. The range ..shared starts at zero and stops before shared. Since that number is no larger than either length, both selected regions stay within their slices. Equality reads those regions; it does not copy their contents into new vectors.

Option<bool> gives three possible answers. Some(true) means the shared bytes agree, Some(false) means at least one differs, and None means there are no shared bytes to check. Returning ordinary true for two empty slices would be valid for a different question about equality. Here it would hide the absence of prefix evidence, which is the distinction we want the reader to see.

The first assertion returns true even though catalog and cat have different lengths. That is the most important limit of this function. Its name and output must be read as an answer about a shared prefix, not as permission to label the responses equal.

Bytes need a common meaning

A displayed word can be represented in several ways. UTF-8 represents text as bytes; some characters need more than one byte. Netscope's reported difference position is a zero-based byte position, not a character number. Position zero names the first byte. A difference inside a multi-byte character should not be interpreted as the same numbered character on screen.

There is another distinction in a capture. Base64 lets an exporter place binary data into a text-based file. Decoding that container representation gives us bytes we can retain. HTTP content encoding, such as gzip, is a separate transformation of the response content. HAR describes text after HTTP decoding and conversion into UTF-8, with optional base64 encoding for storage. A new replay retains bytes without performing those text conversions or content decompression. Decoding base64 alone therefore does not establish that the two representations describe the same stage of processing. See the HAR content description.

The replay client asks for identity encoding and does not decompress a server's response. A server can still return encoded content. If either observation reports a content encoding other than identity, the current comparison declines to judge body bytes. Both previews remain inspectable, but their apparent similarity is not promoted into a comparison result. Supporting more representations would require an explicit decoding policy and limits on the decoded data.

Match header names without erasing their values

Content-Type and content-type name the same HTTP field; field names are case-insensitive. Their values need their own rules. Netscope groups names without changing the stored value bytes, and compares repeated values in their recorded order. This is a comparison of stored values, rather than an attempt to determine every field's semantic equivalence. The distinction follows HTTP's separate rules for field names and field values.

For example, if two values under the same name appear as one, then two on the left and two, then one on the right, this comparison reports a difference. It does not sort those values to manufacture a match. Nor does it combine repeated fields or split values at commas. A name absent from one stored list is labelled there; if no replay headers arrived at all, the comparison says that instead.

Values remain hidden until you press v. Revealing them is a display choice and does not change the comparison. Esc returns to the result and resets masking, so a later visit does not unexpectedly reveal values you previously inspected.

How does a server receive the text we submit?

You want to create a book entry on a local server. The title is café. Typing those four letters into a field feels like a complete description of the input, but the connection carries bytes. Before sending, the client must decide how those letters become bytes, how the server will interpret them, and where the request body ends.

A POST request carries the data we want the server to process. The destination determines what processing means: one endpoint might create a record, another might validate text and return an explanation. Selecting POST does not establish what that particular server will do. That is why Netscope keeps the destination, method, and body together in review before the explicit Send action.

Text already has a byte representation

Rust's String stores text using UTF-8. UTF-8 is an encoding: a rule for representing Unicode text with bytes. ASCII letters such as c, a, and f each use one byte. The precomposed é in this example uses two. The title therefore occupies five bytes even though it looks like four letters.

rust · teaching example
fn body_length(text: &str) -> usize {
    text.as_bytes().len()
}

fn main() {
    let title = String::from("café");
    let bytes = title.as_bytes();

    assert_eq!(bytes, &[0x63, 0x61, 0x66, 0xc3, 0xa9]);

    assert_eq!(title, "café");
}

The parameter text: &str accepts borrowed UTF-8 text. The & in body_length(&title) lends access to the existing String; Rust can view its contents as the string slice the function expects. The function returns a usize, the integer type used for lengths and indexes. Calling len() on the borrowed byte slice counts its bytes. Calling len() directly on a String would also count bytes, but the extra step here makes the representation visible.

In the assertion, 0x introduces a hexadecimal number. Square brackets make an array containing five byte values, and the leading & lends that array for comparison. Reading through bytes has not moved or changed title, so the last assertion can still inspect the original String. No second text buffer is needed just to count the bytes.

A length describes the bytes we actually send

Content-Length is an HTTP field that describes a content length in bytes. Counting letters would make the field wrong for this example. A receiver using a too-small declared length could reach what it believes is the end before receiving the entire intended body. The client must keep framing information consistent with the actual outgoing representation. HTTP defines this byte-count meaning in its Content-Length rules.

Netscope calculates this field from the reviewed UTF-8 body. It does not let a captured Content-Length override the new count. A body copied from a recording may have been edited, and its previous length would no longer describe it. Empty plain text is also a definite body: for POST, its declared length is zero.

GET stays bodyless in this replay profile. Changing the method to POST begins a new plain-text body. Changing back to GET clears it. This is a rule of the editor's supported profile, so the interface does not quietly keep text that it would then omit when sending.

What does moving one character mean?

You reopen a saved request and notice a typo in the middle of its body. Moving Left to fix it seems simple: go back one character, remove the mistake, and type the correction. But the word “character” hides several different units. A byte belongs to storage. A Unicode value identifies a piece of text. What looks like one character on screen can contain more than one such value.

An editor needs to decide which unit a key operates on. Otherwise, correcting a title could split a letter from its accent or leave half of a joined emoji behind.

One visible letter can have two parts

The previous text lesson used a precomposed é, stored as two UTF-8 bytes. Another spelling uses an ordinary e followed by a combining acute accent. Those are two Unicode scalar values: individual values that Rust's char type can represent. Together they form a grapheme cluster, a group of text elements treated as one unit for this editor's movement and deletion.

The drawing compares the spellings. The byte values are illustrative hexadecimal values, not a network measurement. The visual result depends on the font, but the stored sequences are different.

A byte position needs a rule

A cursor can be stored as a usize holding a byte position in a String. That number alone does not establish that the position is suitable for editing. The program must keep it at an allowed boundary.

Here is a small fragment using borrowed text; its statements can run inside main. It distinguishes a byte count, a scalar-value count, and a grapheme count without creating an editor.

rust · teaching example
use unicode_segmentation::UnicodeSegmentation;

let letter = "e\u{301}";

assert_eq!(letter.len(), 3);
assert_eq!(letter.chars().count(), 2);
assert_eq!(letter.graphemes(true).count(), 1);

assert_eq!(letter.get(0..1), Some("e"));
assert_eq!(letter.get(1..2), None);

The escape \u{301} writes the combining accent by its Unicode value. It becomes part of the string rather than the literal backslash and digits. chars() returns an iterator, a sequence we can visit one item at a time; count() consumes that sequence and counts its items. The imported trait makes graphemes() available on the string slice. Its true argument selects extended grapheme rules.

The range 0..1 includes byte zero and stops before byte one. It ends after the e, so get can return that valid UTF-8 substring, wrapped in Some. The range 1..2 ends inside the accent's encoding, so get returns None. Rust's checked string access lets the caller handle such an invalid range without a panic.

Notice that valid UTF-8 is not the editor's complete rule. The first slice succeeds, yet it separates the base letter from its accent. Netscope therefore obtains cursor positions from grapheme boundaries, rather than assuming every valid Rust string boundary is a suitable place for Left or Right to stop.

The editor checks boundaries again after a mutation. If the intended byte position now lies inside a group, it advances to that group's end. Backspace can then remove the whole group. Deleting text can also join its neighbours, so the same check applies after deletion.

String insertion itself uses a byte position. It can move the following bytes to make room, and it requires a valid text boundary. The String insertion documentation describes that requirement. Tracking a checked position is what lets the editor use that operation predictably.

This does not mean every edit takes constant work. Finding boundaries and shifting the remaining bytes both involve examining or moving text. The field's existing size limit bounds the amount of text involved; this editor does not claim the design of a large document editor.

Storage positions are not screen columns

Even a correct byte position does not directly locate the terminal cursor. A CJK character may occupy two terminal columns. A combining mark may add no column. Netscope also displays control characters using visible escapes, so one stored newline appears as several printable symbols rather than moving the terminal to another line.

The display therefore takes the text before the insertion point, escapes it, and measures how that representation wraps in the available width. That produces a row and column. Making the terminal narrower changes those coordinates without changing where the cursor belongs in the String.

When the cursor moves out of view, the editor scrolls to keep it visible. At the end of an exactly full row, it reserves a blank display row for the cursor. The blank row is not a newline inserted into the request. This is another distinction between the text being edited and the screen used to show it.

Terminal emulators and fonts can differ in their rendering. The application uses one consistent width model for wrapping and cursor placement; it does not claim that every emoji will look identical everywhere.

Make a correction without changing the operation

Open a body field and type a short title with an accented letter. Move Left and Right, then remove a group with Backspace or Delete. Use Home to reach the beginning and End to reach the end of the whole field. Predict whether each action changes the body, just the cursor, or neither because the cursor is already at a boundary.

Press Esc and reopen the field. The saved draft should still contain its previous body, because the abandoned edit was a separate value. Repeat the correction and press Enter to save it. You must still review and explicitly Send before any request leaves the program.

The same movement works in URLs, header fields, saved names, and paths. The keyboard contract records precise key behaviour and limits. The cursor operations maintain text boundaries, while the editor translates them into a visible insertion point.

How can a program remember a request after it closes?

You spend a few minutes preparing a request for a local book server. The address is right, the JSON body contains the title you wanted, and review shows the expected byte count. Then you close the program. Tomorrow, you would like to start with that same request rather than type it again.

The editable String values belonged to the running program. A later run does not inherit them. To carry information across that boundary, the program must write a representation of the request somewhere that survives its exit. A file gives the next run bytes it can read; it does not preserve the original Rust objects or bring a network connection back to life.

Choose what should survive

A saved request needs its destination, method, headers, and body. A name helps you recognise it. It does not need the screen's scroll position or a worker that once sent it. Nor should opening the file count as permission to send again: the destination or your intention may have changed since yesterday.

This drawing separates the two runs. The middle box contains file bytes, while the outer boxes contain values owned by running programs. The arrows describe explicit save and open actions.

Illustrative diagram
Today's process              Local file               Tomorrow's process

Editable request ──save──→ JSON bytes on disk ──open──→ New editable request
       │                                                      │
Review, then Send                                      Review, then Send
       │                                                      │
Today's response                                       A new response

No arrow carries today's response into tomorrow's request. A saved draft is a recipe for an operation, not evidence that the operation happened. Netscope therefore opens it without a captured response and does not offer a comparison with an invented observation.

A file also outlives the privacy boundary of a terminal screen. Someone who can read it can read its body and URL. Netscope omits known credential headers when saving and previews what remains. That omission cannot identify every secret: an ordinary-looking query parameter or JSON member could contain one. Read the preview as the contents of a plain-text file you are choosing to keep.

Turn values into a representation

Serialization means expressing program values in a format that can be stored or transmitted. Deserialization goes the other way: reading that representation to construct values. JSON is useful here because it names fields and can be inspected in a text editor. Serde supplies the Rust machinery that connects data types to formats; a format-specific library handles JSON's spelling. The Serde overview describes this division.

Here is a smaller example with just a note title. It demonstrates the conversion in memory, without creating a file or actually restarting the program.

rust · teaching example
use serde::{Deserialize, Serialize};

#[derive(Serialize, Deserialize)]
struct Note {
    title: String,
}

fn main() -> Result<(), serde_json::Error> {
    let note = Note { title: String::from("café") };
    let encoded = serde_json::to_string(&note)?;
    drop(note);

    let reopened: Note = serde_json::from_str(&encoded)?;
    assert_eq!(reopened.title, "café");
    Ok(())
}

The use line brings two names into scope. The #[derive(...)] attribute asks Rust to generate implementations for the listed traits. A trait describes a capability a type supports; here the capabilities are being serialized and deserialized. The generated implementations know that a Note contains a String field named title.

to_string(&note) borrows the note and creates a separate String containing JSON. drop(note) then consumes the original note and releases its owned text. The encoded String remains alive because it is a different value. Reading it with from_str constructs a new Note with its own title. The annotation reopened: Note tells Rust which type the JSON should become.

Both conversion calls return a Result: either a successful value or an error. The ? after each call extracts success or returns the error from main immediately. The return type names serde_json::Error as the possible failure, while () means successful completion carries no additional value. The last assertion checks that the newly constructed title has the expected text.

A request body that itself contains JSON is still a String inside the saved request. Quotes in that String must be escaped in the outer file. Reading the file removes that outer escaping and restores the body text. It does not parse and rewrite the body's number spelling or whitespace.

A readable file can still be the wrong request

Suppose a file contains a well-formed JSON object with a method named DELETE. The parser can understand its punctuation, but this Netscope profile supports only GET and POST. Successful parsing and a supported request are separate checks.

A version field gives the format an explicit identity. Version 1 tells the reader which fields and meanings to expect. If a future version changes those meanings, an older program should report that it does not understand the version. Guessing could produce a different request from the one you meant to keep.

Netscope checks the file's size, structure, version, and request values before opening an editor. It rejects unexpected fields rather than quietly ignoring a possible misspelling. Those checks make failure recoverable: the original file remains available to inspect, and no network operation has begun.

Why use a file instead of a database?

For one named request, a versioned JSON file is easy to inspect, copy, and reopen without starting another service. A database could also run locally and would become useful if we needed to search a large saved collection or update several records together. It would introduce a schema, the rules for stored records, and a migration policy for changing those rules.

The current file format makes a smaller promise. It carries one request's values between runs. It does not coordinate two people editing that request, remember a history of revisions, or guarantee that an unknown future format can be read. The version field lets us reject a format we do not understand instead of guessing its meaning. If saved collections or concurrent editing become requirements, the storage decision should change with them.

Replacing a file has a vulnerable middle

Imagine that yesterday's file is valid. Today you save an edited body, but a write fails halfway through. If the program had erased the old file first, you could be left with neither yesterday's request nor today's complete replacement.

The safer sequence keeps the old destination while building a separate file beside it. Read the diagram from top to bottom; replacement happens only after the new content has been written and synchronized.

Illustrative diagram
book.json: yesterday's complete request
    │
    ├── create book.json.netscope-tmp without replacing an existing file
    ├── write today's complete representation
    ├── synchronize the new file's contents
    │       failure here → keep yesterday's file
    └── rename the completed temporary file to book.json
            success → the destination names today's complete request

Rust's File value owns an open-file handle: access that the operating system has granted to a file. Leaving its scope closes that handle, but closing alone does not report every storage failure. The explicit synchronization step can return an error before replacement. See the standard library's File and synchronization documentation.

Keeping the temporary file beside the destination also keeps the rename within the same filesystem. Rename can replace an existing file, but it can fail, so the program must still handle its Result. The rename documentation explains the platform restrictions. This sequence protects against an ordinary partial-write failure; it is not a promise that every filesystem survives sudden power loss the same way.

If the process stops abruptly before replacement, a temporary file may remain. Netscope refuses to overwrite it automatically. That makes the conflict visible and leaves you a chance to inspect what was written.

Predict what will return

Prepare a local request, press w from its draft, choose a name and path, and inspect the save preview. After confirming, close Netscope and reopen the file using the saved-draft walkthrough.

Before opening, predict three things: whether the body will still contain its line breaks, whether an authorization header will be present, and whether a request will be sent. The body should survive exactly; a known credential header should be absent; opening alone should send nothing. Those outcomes follow from what the file contains and what opening is allowed to do.

The saved-draft contract records the precise fields, limits, and filesystem assumptions. The saved-value model handles representation and validation, while the file operations handle reading and replacement.

Where should a change belong?

Suppose you want to add a second capture format. The new file describes the same kinds of requests, but arranges its fields differently. Should that force you to rewrite the terminal screen, the host summaries, and the request editor?

The answer depends on where the program draws its boundaries. Architecture is the set of choices about responsibilities, dependencies, and ownership that make some changes local and others expensive. It is easier to judge those choices through a concrete change than through a list of pattern names.

By this point in the book, we have followed a recording into a session, opened a request, sent a separate draft, and saved it. We can now ask why those operations are arranged as they are, and when another arrangement would serve us better.

Keep a file format away from a screen's decisions

The importer understands HAR fields and validates the parts Netscope consumes. It produces a session containing requests in the program's own representation. Drawing reads that representation, so it need not know where a browser placed a particular JSON field.

We could instead let each screen read JSON directly. That might shorten the first prototype, but every screen would need to handle missing fields, wrong types, and browser variations. Two screens could end up interpreting the same record differently. A common representation gives those checks one place to happen.

There is a cost. The representation must change when we decide to retain something new, and converting the parsed file into owned request values requires allocations. An allocation is memory the program requests for data such as a string or vector. During import, parsed JSON and the growing session can both occupy memory. A byte limit on the file is therefore not a promise that total memory stays below that same number.

A different format would need to produce the same meanings, not merely fill fields with vaguely similar numbers. If it cannot distinguish an unavailable duration from zero, the importer must preserve that uncertainty. The shared model is useful only while its distinctions remain honest.

Make dependencies point toward the data rules

A Rust crate is a unit the compiler builds. A library crate exposes code for other crates to use; a binary crate produces a runnable program. Netscope groups its work into four packages in one Cargo workspace. The packages make their dependencies explicit.

In this diagram, an arrow means “uses code from,” not “sends a network message to.” The terminal package coordinates the other pieces; the common data rules do not depend on the terminal or network packages.

Illustrative diagram
netscope-tui ───────────────► netscope-core
     │                            ▲
     ├──► netscope-import ────────┤
     │                            │
     └──► netscope-net ───────────┘

The core package holds the session, draft rules, comparisons used by offline analysis, and saved-value representation. Import knows how to read HAR. Net handles a reviewed send and its result. Tui contains terminal drawing, input, the command entry point, and local saved-file operations. These are responsibility boundaries, not four separate running processes.

A single crate with modules could express much of the same organization with fewer manifests and less public API. Four packages are not inherently more mature or faster. Here they make it harder for an ordinary data rule to accidentally depend on terminal input or a live socket, and allow focused tests to use that rule without starting either. Core still uses libraries for URLs and serialization; independence from I/O does not mean independence from all libraries.

The boundaries are also imperfect. File operations currently live beside terminal coordination. If a second interface needs them, that placement may deserve revision. Splitting every small helper into its own package would create more boundaries to maintain without necessarily improving the user's experience.

Create a value where its lifetime is understood

Imagine opening two recordings in separate views. Each view needs to retain its own requests. Explicitly constructing two sessions makes that relationship straightforward: each caller receives and owns its session.

A constructor is a function that creates a value. In Rust, names such as Session::new are ordinary associated functions: functions named through a type. Rust does not give new a special construction privilege. A factory is a broader creation role, often used when the caller should not need to choose the concrete implementation. A singleton is a policy that restricts something to one instance in a chosen scope, often accessed globally. Creation and instance count are different questions, so “factory versus singleton” is not automatically a meaningful choice.

A global session could avoid passing references through functions, but then the current recording would be a hidden dependency. Tests would need to coordinate resets, and a second open capture would need a new arrangement. Explicit owners and parameters keep that dependency visible. They cost some argument passing, which is a reasonable exchange for independent sessions.

Today Netscope has a concrete transport and straightforward construction functions. It does not have an abstract factory selecting among interchangeable HTTP clients. Tests substitute a smaller boundary where needed, such as an in-memory stream for a network exchange. That substitution lets a test control bytes without requiring a second full HTTP implementation.

An interface that selected a real transport or a simulator might become useful if both existed and callers genuinely needed to choose. Adding that layer now would mean maintaining another contract for a hypothetical second implementation. Conversely, a process-wide immutable resource might reasonably be initialized once and shared. The current TLS configuration is constructed for each send and shared through Arc; it is not a global client singleton. That costs repeated setup, so reuse is a possible future measurement-driven change.

Represent the alternatives the reader can distinguish

Suppose a request body is absent from the recording. Another body is present but empty. Storing both as an empty string would make later code unable to explain the difference. The model uses named alternatives because the user needs those outcomes to remain distinct.

Enums help express those alternatives. Structs group values that belong together. A source request ID stays separate from a row's position because filtering changes positions without changing captured identity. These choices allow the compiler to reject some mistakes and make others easier to test.

They do not make every application rule automatic. A request ID from another session can still have an in-range number. The current constructor expects already validated request values; its name alone does not prove they came through the importer. The editor's screen mode is an enum, but other fields still have to agree with that mode. We use tests and controlled construction paths for rules the types do not fully enforce.

We could build more restrictive types that make invalid construction harder. That would add conversions and more types to learn. We should do so when a concrete misuse or growing API makes the additional restriction valuable, rather than claim that the present model makes all invalid states impossible.

Spend memory to avoid repeating a question

Opening Hosts asks for counts and an ordered list of requests for each host. Recomputing them on every keypress would repeatedly examine the same capture. Netscope instead prepares those summaries when it builds the session.

The advantage follows from a condition: the capture does not change while you browse it. The summaries can remain valid. We spend additional memory on counts and lists of IDs, but those lists do not duplicate every request body. Redirect and retry analysis likewise keeps candidate IDs rather than copying complete requests.

A live capture would change the calculation. New records could make an earlier summary or candidate list incomplete. We would need to update derived values, rebuild them, or calculate them when requested. Similarly, very large offline captures might favour delaying an expensive analysis until its view is opened. That saves initial work at the cost of a pause later.

The recent overlap optimization changes how quickly we locate eligible candidates, not which candidates qualify. Sorted start times allow a search to skip the whole range before a request's reported end. Other comparisons can still be expensive. The measurement reference records actual samples and the remaining limits; a data structure's name alone is not performance evidence.

Distinguish a reason from a story added later

A useful decision explanation has a constraint and a consequence. “The capture stays unchanged, so we can calculate its summaries once” supplies both. “We use this pattern because it is best practice” supplies neither.

Some project choices were documented before implementation, such as the replay transport contract. Other reasons in this chapter are an assessment of the code during the architecture audit. That assessment can reveal a reasonable tradeoff, an unresolved question, or unnecessary complexity. It should not pretend that all alternatives were benchmarked or discussed before the code existed.

The architecture decision record distinguishes those cases. It links the implementation and evidence, names plausible alternatives, and states what would make us revisit a choice. It also records open issues, including the process-global operation counter. This lets the book teach the reasoning without turning each chapter into a maintenance log.

Then change the requirement to a capture that grows while you watch it. Explain why that second change reaches beyond parsing into identity, summaries, and ownership.

Knowing whether the program is right

A request can appear on screen with the wrong timing. The program might compile, open the file, and draw every row while still turning an unavailable value into zero. What would tell us that the behaviour is wrong?

We need to state what a small, controlled input should produce. That expectation gives a test something meaningful to check. Other tools answer different questions about the code, and understanding their limits helps us use them well.

The compiler checks Rust's rules

The compiler rejects using a string after it has moved and passing a host ID where a request ID is required. These are rules expressed by the language and our types.

It cannot decide whether we have interpreted a HAR timing correctly unless we express that interpretation in the program. A missing timing converted into zero can be perfectly valid Rust and still be incorrect for our purpose.

This is why a successful build matters but does not finish the check. We also need evidence about the meaning of the result.

A test makes an expectation precise

Take the optional timing -1. We expect the importer to retain it as unavailable. A test supplies that value and compares the result with the unavailable variant. If the importer changes it to zero, the comparison fails.

A useful test protects a distinction someone cares about. In this project, examples include preserving duplicate headers, returning to the same selected request, and distinguishing an empty body from an unrecorded body.

We use invented capture data for these checks. A fixture is a saved test input with a known purpose. Small fixtures make it possible to understand why a result is expected rather than trusting a large recording no one has read closely.

Control the inputs that affect the answer

A deterministic test produces the same observable result from the same controlled inputs. Sorting three requests with fixed timestamps is a good example. Equal timestamps need an explicit tie rule, or a change in ordering could make the selected request appear to jump.

A test that depends on a public server has more inputs than its source file reveals. The server can change its response, fail, or reply at a different speed. Most of Netscope's current tests therefore use local synthetic data and screen buffers held in memory.

Time needs the same treatment when it becomes part of the behaviour. To test whether a cookie has expired, supply the time used by the check. Then test just before expiry, at expiry, and after expiry. Waiting for a real clock to cross the boundary makes the experiment harder to repeat.

Check the rule and the visible result

Navigation tests apply actions to view state and check which request remains selected. Drawing tests inspect the resulting terminal cells at fixed sizes. The two checks support different claims: the intended request can be selected even if the screen fails to show that selection clearly.

Terminal restoration needs another kind of evidence. An in-memory screen cannot prove that the terminal's input mode was restored. The separate terminal check opens a controlled pseudo-terminal, runs the viewer, and inspects the modes and restoration commands after exit.

That integration check involves the operating system and uses a timeout. We keep it separate from the deterministic state and buffer tests, so a reader can tell exactly what each result establishes.

Use linting for recurring code concerns

A lint is an automated check for a code pattern that deserves attention. Clippy is Rust's linting tool. It can catch common mistakes and suggest clearer forms; it cannot decide whether an explanation is suitable for a beginner.

The workspace, our group of related Rust packages, also uses a formatter for consistent code layout and documentation tests that compile the marked examples. It fixes the Rust toolchain version and retains a dependency lockfile, which records the dependency versions chosen for the application. Those choices reduce accidental differences between development environments.

Our lint rules forbid unsafe code and deny unhandled results that must be used. They also restrict unwrap and expect, which can panic on failure. A rejected capture should produce a useful error message, so that rule supports a visible requirement rather than merely imposing a style preference.

The exact rules and check commands belong in the development guide. A chapter should explain why the checks matter without requiring you to memorise their flags.

Let comments explain a reason

A comment such as Loop over requests repeats what a loop already says. A comment such as Keep source order so equal timestamps stay stable explains a decision that may be less obvious.

Use familiar words in comments and keep the explanation near the relevant code. Longer lessons belong here, where a reader has room to follow the idea and an example. Passing a linter cannot establish that either explanation is clear.

Design a small experiment

Choose one distinction: missing versus zero timing, an empty versus absent body, or source order versus display order. Describe the smallest input that exercises it and the exact result you expect.

Then describe a plausible bug that would make the test fail. If your test would still pass with that bug present, revise the expectation. The verification record shows which experiments the current suite actually performs.

How this book should read

This book is for a reader who knows no Rust. Its job is to make a technical idea understandable, then help the reader recognise that idea in a working program. The reader's questions determine the sequence. Code supplies concrete examples and evidence once there is a reason to study it.

This applies to every existing chapter and every chapter added later. An implementation change is a reason to check the explanation's accuracy, not an instruction to organise the explanation around new functions or files.

Start with something the reader can reason about

A useful opening gives the reader a situation: a missing measurement, a selected request, or text that needs to remain alive while another function reads it. Develop the question before naming the language feature that helps answer it.

For example, beginning a screen chapter with App::apply matches Screen and Action requires the reader to decode several program names. Beginning with a selected request that should remain selected after Esc establishes the behaviour first. An enum and a small state value then have a purpose the reader can explain.

The detail still matters. Once ownership appears, explain which value owns the data, what moves, what remains in place, and when cleanup happens. A short slogan about safety cannot replace that account.

Be precise without making the prose dense

Use ordinary words where they express the idea accurately. Introduce a technical term when it lets us name something useful, and explain it at that first use. Continue using the same name so the reader does not have to decide whether a new synonym describes a new concept.

Give sentences enough room to express cause and consequence. Short sentences can establish a rule; a longer sentence can explain the condition under which it applies. Avoid both compressed notes and paragraphs that introduce several unfamiliar concepts at once.

Simplicity does not require removing the mechanism. "A shared reference lets this function read the request while its owner keeps the data alive" is concrete. It tells the reader what access is granted and where responsibility remains. Follow it with a small example and a consequence the reader can predict.

Let examples earn their place

Use the book request as a running example when it helps connect ideas. Choose the smallest code fragment that demonstrates the current question. Explain new syntax close to the fragment, and show or describe the expected result.

Introduce another concept only when the explanation needs it. A vector example does not need to teach chained transformations of optional values at the same time. That extra syntax can wait until the reader has a reason to ask about it.

When an illustration differs from the application, say so near the example. Once the idea is clear, link to the actual source for readers who want to examine the complete version. Keep test counts, detailed build flags, and changing implementation inventories in reference material.

Use diagrams to explain a relationship

The ownership drawing shows one text allocation as responsibility moves between names. A navigation drawing shows what changes when a request opens and what remains available when the reader returns. Each figure should answer a question that prose alone makes harder to follow.

Introduce the diagram before asking the reader to interpret it. Explain what its arrows mean and what the reader should notice. Label illustrative data so a precise-looking drawing does not imply a measurement or a guaranteed memory layout.

The visual direction uses charcoal, mint, thin rules, and numbered figures, with chapter navigation and a local outline. Prose uses proportional type; code and technical labels use monospace. The layout should help sustained reading as well as quick lookup.

Review the explanation before adding detail

Read the chapter from its opening with no source file beside it. Can a newcomer explain the problem, follow the example, and predict one consequence? Check every unfamiliar term and symbol. If understanding requires an unexplained name from the repository, add the missing explanation or move the detail to a reference.

Then check the technical claims against the implementation. This second pass catches stale facts without turning the chapter into a code tour. A refactor that preserves behaviour may require a source-link correction and no change to the lesson's structure.

Exercises should follow naturally from the explanation. Ask the reader to predict a result, make a small change, or explain a choice. Provide enough setup to attempt the exercise without guessing how to run the example. Compilation checks can catch broken snippets; they cannot establish whether the prose teaches well.

Explain why a design fits, and when it would not

A material architecture choice needs more than a description of the implementation. Explain the concrete constraint, a plausible alternative, and the consequence of choosing one. Distinguish a reason documented at the time from an assessment made during a later audit. Do not invent a rejected alternative or a performance result to make existing code sound inevitable.

Teach the reasoning in the chapter where the reader needs it. Keep dates, evidence links, and revisit conditions in the architecture decision record. Record unresolved choices honestly; an unnecessary atomic or an awkward ownership boundary is a reason to investigate, not an obligation to defend it. A code change should update the relevant decision and lesson when it changes the explanation, while preserving the reader's sequence.
